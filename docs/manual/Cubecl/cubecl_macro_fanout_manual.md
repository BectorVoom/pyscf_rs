# Detailed Summary: Reducing CubeCL Macro Fan-out and Generated Rust Code

## 1. Purpose of the Manual

This manual explains how to reduce build time in CubeCL-based scientific computing projects by minimizing the amount of Rust code generated by CubeCL procedural macros.

CubeCL uses the `#[cube]` procedural macro to parse Rust-like kernel code and generate Rust-side expansion functions. These expansion functions build CubeCL’s intermediate representation, or IR, which is later used to generate GPU or CPU kernels.

Because `#[cube]` can be applied to:

*   functions
*   traits
*   impl blocks

and because `#[cube(launch)]` additionally generates launch wrappers, careless usage can cause a large increase in:

*   generated Rust code
*   procedural macro work
*   Rust compiler workload
*   LLVM IR size
*   binary size
*   build time
*   compile-time error complexity

The main goal is to keep CubeCL’s macro expansion surface small while preserving runtime performance.

***

## 2. Core Concept: Macro Fan-out

In this context, **macro fan-out** means the amount of code generation and compiler work triggered by CubeCL macros such as:

*   `#[cube]`
*   `#[cube(launch)]`
*   `#[cube(launch_unchecked)]`
*   `#[derive(CubeType)]`
*   `#[derive(CubeLaunch)]`

High macro fan-out usually comes from:

*   too many launchable kernels
*   large `#[cube]` functions
*   excessive use of `#[cube]` traits and impl blocks
*   duplicated kernels for each numeric type
*   overuse of derive macros on internal types
*   encoding runtime or JIT-time choices as Rust type-level variants
*   using const generics or associated constants where `comptime` would be better
*   enabling too many backend features during normal development

The result is often slower `cargo build`, slower `cargo check`, larger binaries, and harder-to-debug macro expansion failures.

***

## 3. Main Design Principle

The most important rule is:

> **Keep the CubeCL expansion surface as small as possible.**

In practice, this means:

*   expose only a small number of launchable kernels
*   use plain `#[cube]` only where CubeCL expansion is truly needed
*   avoid unnecessary `#[cube]` traits and impl blocks
*   avoid duplicating kernels by numeric type
*   move constants and policy decisions into `comptime`
*   keep derive macros limited to true CubeCL boundary types
*   reduce Rust-side type-level variation
*   let CubeCL JIT handle specialization where appropriate

A good architecture separates:

```text
Host API surface:
  Small and stable

CubeCL launch surface:
  Minimal number of true entry kernels

Internal kernel logic:
  Small, generic, function-based #[cube] helpers

Specialization:
  Handled through #[comptime], comptime!, #[define], and CubeCL JIT
```

***

# 4. Understanding `#[cube]` vs `#[cube(launch)]`

## 4.1 `#[cube]`

`#[cube]` is the general CubeCL expansion macro.

It can be used on:

*   helper functions
*   traits
*   impl blocks
*   kernel-internal reusable logic

It generates Rust expansion code that builds CubeCL IR.

## 4.2 `#[cube(launch)]`

`#[cube(launch)]` generates more code than plain `#[cube]`.

It creates:

*   the CubeCL expansion function
*   host-side launch wrapper code
*   additional launch-related API surface

Therefore, it should be used only for functions that are actually launched from host Rust code.

## 4.3 Recommended Pattern

Use `#[cube(launch)]` only for true entry kernels:

```rust
#[cube(launch)]
fn saxpy_kernel<F: Float>(
    x: &Array<Line<F>>,
    y: &mut Array<Line<F>>,
    a: F,
) {
    if ABSOLUTE_POS < x.len() {
        y[ABSOLUTE_POS] = saxpy_inner(x[ABSOLUTE_POS], y[ABSOLUTE_POS], a);
    }
}

#[cube]
fn saxpy_inner<F: Float>(x: Line<F>, y: Line<F>, a: F) -> Line<F> {
    a * x + y
}
```

Avoid marking internal helpers as launchable:

```rust
#[cube(launch)]
fn helper_1(...) { ... }

#[cube(launch)]
fn helper_2(...) { ... }
```

If these helpers are never directly launched from the host, they should be plain `#[cube]` functions.

# 5. Reduce the Number of Launch Kernels

Every `#[cube(launch)]` function increases the generated launch surface.

A common anti-pattern is creating one launch kernel per small variation:

```rust
#[cube(launch)]
fn conv3x3_f32(...) { ... }

#[cube(launch)]
fn conv5x5_f32(...) { ... }

#[cube(launch)]
fn conv7x7_f32(...) { ... }
```

This multiplies macro expansion and launch wrapper generation.

A better approach is to collapse variants into one generic launch kernel and use `#[comptime]`:

```rust
#[cube(launch)]
fn conv<F: Float>(
    input: &Array<F>,
    weight: &Array<F>,
    output: &mut Array<F>,
    #[comptime] kernel_size: u32,
) {
    if comptime!(kernel_size == 3) {
        // IR for 3x3
    } else if comptime!(kernel_size == 5) {
        // IR for 5x5
    } else {
        // fallback
    }
}
```

This keeps Rust-side generated code smaller while still allowing CubeCL to specialize kernel IR.

***

# 6. Prefer Generic Numeric Kernels

## 6.1 Problem

A major source of fan-out is writing separate kernels for each numeric type:

```rust
#[cube]
fn reduce_step_f16(x: Line<f16>, y: Line<f16>) -> Line<f16> {
    x + y
}

#[cube]
fn reduce_step_bf16(x: Line<bf16>, y: Line<bf16>) -> Line<bf16> {
    x + y
}

#[cube]
fn reduce_step_f32(x: Line<f32>, y: Line<f32>) -> Line<f32> {
    x + y
}
```

This duplicates the same algorithm across concrete types.

## 6.2 Recommended Pattern

Use generic numeric traits such as:

*   `Float`
*   `Int`
*   `Numeric`

Example:

```rust
#[cube]
fn reduce_step<F: Float>(x: Line<F>, y: Line<F>) -> Line<F> {
    x + y
}
```

If the algorithm is structurally identical across numeric types, keep one generic path.

## 6.3 Why This Matters

CubeCL already supports generic expansion models such as:

*   `FloatExpand`
*   `IntExpand`
*   `NumericExpand`

These help reduce the number of Rust-side expansions needed for different concrete element types.

The ideal direction is:

```text
Bad:
  expand::<f16>()
  expand::<bf16>()
  expand::<f32>()
  expand::<f64>()

Better:
  expand::<FloatExpand>()
  actual element type handled through CubeCL context / launch-time information
```

***

# 7. Use `#[define(T)]` to Avoid Public API Explosion

## 7.1 Problem

If multiple host-visible functions differ only by element type, memory layout, or similar type-level configuration, the public API and generated wrapper code can grow quickly.

For example:

```rust
launch_f16(...)
launch_bf16(...)
launch_f32(...)
launch_f64(...)
```

This creates repeated host APIs and launch wrappers.

## 7.2 Recommended Pattern

Use `#[define(T)]` to map launch-time information to a generic type parameter.

```rust
#[cube(launch)]
fn map_kernel<N: Numeric>(
    input: &Array<N>,
    output: &mut Array<N>,
    #[define(N)] _elem: ElemType,
) {
    if ABSOLUTE_POS < input.len() {
        output[ABSOLUTE_POS] = input[ABSOLUTE_POS];
    }
}
```

This allows one launch entry to cover multiple numeric type choices.

## 7.3 Rule

If multiple launch functions differ only by type choice, try to collapse them into:

```text
one generic #[cube(launch)] function
+ #[define(T)] launch-time specialization
```

***

# 8. Move Constants and Policies into `comptime`

## 8.1 Problem

Rust type-level constants and const generics can increase monomorphization.

For example:

```rust
pub trait TileConfig {
    const M: usize;
    const N: usize;
    const K: usize;
}

#[cube(launch)]
fn matmul<F: Float, C: TileConfig>(
    lhs: &Array<F>,
    rhs: &Array<F>,
    out: &mut Array<F>,
) {
    // Use C::M, C::N, C::K
}
```

Each `TileConfig` implementation may generate another Rust-side instance.

## 8.2 Recommended Pattern

Move such values into `#[comptime]` arguments:

```rust
#[cube(launch)]
fn matmul<F: Float>(
    lhs: &Array<F>,
    rhs: &Array<F>,
    out: &mut Array<F>,
    #[comptime] tile_m: u32,
    #[comptime] tile_n: u32,
    #[comptime] tile_k: u32,
) {
    // Use tile_m, tile_n, tile_k during IR construction
}
```

Good candidates for `comptime` include:

*   tile sizes
*   block shapes
*   line sizes
*   loop unroll factors
*   reduction axes
*   algorithm policy flags
*   scheduling decisions
*   precomputed constants
*   kernel-size variants
*   vectorization parameters

## 8.3 `comptime!`

Use `comptime!` when a value should remain compile-time-only and should not become runtime IR.

Example:

```rust
#[cube]
fn affine<F: Float>(x: Line<F>) -> Line<F> {
    let alpha = F::new(comptime!(1.25f32));
    let beta = F::new(comptime!(0.5f32));
    alpha * x + beta
}
```

## 8.4 Rule

If a value affects code generation or specialization but does not need to be represented in runtime IR, use:

```rust
#[comptime]
```

or:

```rust
comptime!(...)
```

***

# 9. Be Careful with `#[cube]` Traits and Impl Blocks

## 9.1 Problem

CubeCL supports `#[cube]` on traits and impl blocks, but this can generate a broader expansion surface than free functions.

When used on traits, CubeCL may generate:

*   expansion traits
*   method expansion machinery
*   forwarding code
*   impl-related generated code

For small abstractions, this may be overkill.

## 9.2 Expensive Pattern

```rust
#[cube]
trait Activation<F: Float> {
    fn map(x: Line<F>) -> Line<F>;
}

#[cube]
impl<F: Float> Activation<F> for Gelu {
    fn map(x: Line<F>) -> Line<F> {
        // ...
    }
}
```

## 9.3 Prefer Free Helper Functions

```rust
#[cube]
fn gelu_map<F: Float>(x: Line<F>) -> Line<F> {
    let sqrt2 = F::new(comptime!(2.0f32.sqrt()));
    let tmp = x / Line::new(sqrt2);
    x * (Line::erf(tmp) + 1.0) / 2.0
}
```

## 9.4 Rule

Use `#[cube]` traits only when trait-based abstraction is truly necessary inside kernel code.

Otherwise, prefer:

```text
small free #[cube] helper functions
```

***

# 10. Avoid Too Many Tiny `#[cube]` Helpers

There is a balance to maintain.

Splitting very large kernels can improve readability and reuse, but marking every tiny helper with `#[cube]` can also increase macro targets.

Problematic example:

```rust
#[cube]
fn add_bias<F: Float>(x: Line<F>, b: Line<F>) -> Line<F> {
    x + b
}

#[cube]
fn relu<F: Float>(x: Line<F>) -> Line<F> {
    Line::max(x, Line::new(F::new(0.0)))
}

#[cube]
fn normalize<F: Float>(
    x: Line<F>,
    mean: Line<F>,
    inv_std: Line<F>,
) -> Line<F> {
    (x - mean) * inv_std
}
```

Each function becomes a macro expansion target.

## Recommended Balance

Use separate `#[cube]` helpers when they represent meaningful reusable stages.

Example:

```rust
#[cube(launch)]
fn reduce_kernel<F: Float>(
    input: &Array<Line<F>>,
    output: &mut Array<Line<F>>,
) {
    if ABSOLUTE_POS < input.len() {
        let v = load_and_preprocess(input[ABSOLUTE_POS]);
        output[ABSOLUTE_POS] = reduce_local(v);
    }
}

#[cube]
fn load_and_preprocess<F: Float>(x: Line<F>) -> Line<F> {
    x * x
}

#[cube]
fn reduce_local<F: Float>(x: Line<F>) -> Line<F> {
    x
}
```

## Rule

Break apart meaningful algorithmic stages, not every expression-level helper.

***

# 11. Limit `CubeType` and `CubeLaunch` Derives

## 11.1 Problem

Derive macros also generate code.

Applying these derives broadly can increase generated Rust code without providing meaningful benefit.

Avoid this:

```rust
#[derive(CubeType, CubeLaunch)]
struct InternalTemporaryState {
    // ...
}
```

if the type is never passed across a CubeCL boundary.

## 11.2 Recommended Usage

Use `CubeType` and `CubeLaunch` only for:

*   kernel argument boundary types
*   custom IR-visible data types
*   launch-visible structures
*   types that must participate in CubeCL type handling

Avoid deriving them for:

*   host-only helper structs
*   temporary pipeline state
*   internal organizational enums
*   config objects not passed to kernels

## 11.3 Rule

Treat CubeCL derives like FFI boundary derives:

> Apply them only where there is a real boundary requirement.

***

# 12. Reduce Type-Level Kernel Variants

## 12.1 Problem

Encoding every variation as a Rust type creates monomorphization pressure.

Avoid:

```rust
struct Tile16x16;
struct Tile32x32;
struct Tile64x64;

#[cube(launch)]
fn kernel<F: Float, T: TileConfig>(...) {
    // ...
}
```

This causes Rust to create separate instances for each `T`.

## 12.2 Prefer `#[comptime]`

```rust
#[cube(launch)]
fn kernel<F: Float>(
    ...,
    #[comptime] tile_m: u32,
    #[comptime] tile_n: u32,
) {
    // ...
}
```

## 12.3 Rule

Do not represent every combination as Rust types:

```text
dtype × shape × backend × tile size × algorithm variant
```

Instead, push suitable variation into CubeCL JIT-time specialization.

***

# 13. Reduce Element-Type Generic Explosion

## 13.1 Problem

A kernel like this may look elegant, but it can create many type combinations:

```rust
#[cube(launch)]
fn kernel<F: Float, G: Float, Acc: Float>(
    input: &Array<F>,
    weight: &Array<G>,
    output: &mut Array<Acc>,
) {
    // ...
}
```

If `F`, `G`, and `Acc` can each be `f16`, `bf16`, `f32`, or `f64`, the number of combinations grows quickly.

## 13.2 Better Direction

Reduce the number of type parameters at launch boundaries.

Where possible:

*   use one generic element type
*   use `#[define]`
*   use CubeCL expansion types
*   move actual element type decisions to launch-time context
*   avoid element-type-dependent trait parameters at the boundary

## 13.3 Family Pattern

Instead of directly parameterizing instruction traits by element type at the launch boundary, use a family abstraction.

Less desirable:

```rust
#[cube(launch)]
fn matmul<F: Float, I: Instruction<F>>(
    lhs: &Array<F>,
    rhs: &Array<F>,
    out: &mut Array<F>,
) {
    I::execute(lhs, rhs, out);
}
```

Improved direction:

```rust
pub trait InstructionFamily {
    type Instruction<F: Float>: Instruction<F>;
}

pub trait Instruction<F: Float> {
    fn execute(lhs: Matrix<F>, rhs: Matrix<F>, out: Matrix<F>);
}

#[cube(launch)]
fn matmul<F: Float, I: InstructionFamily>(
    lhs: &Array<F>,
    rhs: &Array<F>,
    out: &mut Array<F>,
) {
    I::Instruction::<F>::execute(/* ... */);
}
```

The idea is to reduce the number of Rust-side generic combinations exposed directly at the launch boundary.

***

# 14. Manage Debug-Only Expansion

CubeCL may support debug-oriented expansion features such as:

```rust
#[cube(debug_symbols)]
```

These are useful when debugging IR generation or source mapping, but they can increase compile-time work.

## Recommended Policy

*   keep debug symbol generation off by default
*   enable it only for focused debugging
*   use a dedicated debug profile or environment variable
*   do not leave debug-heavy expansion enabled in CI unless necessary

***

# 15. Reduce Feature Combinations

CubeCL can support multiple backends, such as:

*   WGPU
*   CUDA
*   ROCm
*   Metal
*   Vulkan
*   CPU

Enabling all features during normal development can increase the dependency graph and build workload.

Avoid:

```toml
[dependencies]
cubecl = { version = "0.9", features = ["wgpu", "cuda", "rocm", "default", "std"] }
```

Prefer enabling only what is needed:

```toml
[dependencies]
cubecl = { version = "0.9", default-features = false, features = ["std", "wgpu"] }
```

For CI, prefer separate backend jobs instead of always building everything with:

```bash
cargo build --all-features
```

***

# 16. Split Crates to Reduce Recompilation Scope

A good workspace structure separates macro-heavy CubeCL code from ordinary application logic.

Example:

```text
workspace/
  crates/
    app/
      Cargo.toml
      src/main.rs

    core/
      Cargo.toml
      src/lib.rs

    kernels/
      Cargo.toml
      src/lib.rs
      src/matmul.rs
      src/conv.rs

    kernel_config/
      Cargo.toml
      src/lib.rs
```

## Recommended Structure

*   Put most `#[cube]` code in a dedicated `kernels` crate.
*   Keep application logic outside the macro-heavy crate.
*   Avoid exposing too many public generic APIs from the kernel crate.
*   Put stable config types in a separate crate if they change less often.
*   Minimize features in the kernel crate.
*   Design stable APIs so UI, CLI, and I/O changes do not force CubeCL kernels to rebuild.

# 17. Cargo Profile Optimization

CubeCL projects can benefit from lighter development profiles.

## Recommended Development Settings

```toml
[profile.dev]
debug = "line-tables-only"
incremental = true

[profile.dev.build-override]
opt-level = 0
codegen-units = 256
debug = false
```

Another possible lightweight setup:

```toml
[profile.dev]
opt-level = 0
debug = 1
incremental = true
codegen-units = 256

[profile.test]
opt-level = 0
debug = 1
incremental = true
codegen-units = 256
```

## Why This Helps

Proc macros and build dependencies can be configured separately through Cargo profile overrides.

This can reduce development-time compilation cost, especially when the goal is correctness checking rather than performance benchmarking.

## Separate Benchmark Profile

Use a separate profile for performance validation:

```toml
[profile.bench-fast]
inherits = "release"
debug = 0
lto = "off"
codegen-units = 16
```

Do not use the same profile for:

*   fast development checks
*   correctness tests
*   final performance benchmarking

Each has different build-time and runtime-performance tradeoffs.

# 18. Measurement Workflow

Do not optimize blindly. Measure before and after each change.

## 18.1 Use Cargo Timings

```bash
cargo clean
cargo build --timings
```

Inspect the generated HTML report, typically located at:

```text
target/cargo-timings/cargo-timing.html
```

Look for:

*   slow CubeCL-heavy crates
*   crates on the critical path
*   long codegen time
*   repeated builds due to feature differences
*   build serialization caused by proc macros
*   excessive link time

***

## 18.2 Inspect Expanded Code

Use `cargo expand`:

```bash
cargo install cargo-expand
cargo expand -p your_kernel_crate > expanded.rs
wc -l expanded.rs
```

Look for:

*   too many generated launch wrappers
*   overly large expanded files
*   excessive trait expansion
*   many small `#[cube]` helper expansions
*   duplicated kernels by dtype or variant

***

## 18.3 Use Macro Statistics

On nightly Rust:

```bash
cargo +nightly rustc -p your_kernel_crate -- -Zmacro-stats
```

This helps identify:

*   which macros generate the most code
*   whether CubeCL macros dominate expansion
*   whether traits or impls are major contributors
*   whether refactoring actually reduces macro output

***

## 18.4 Compare Before and After

After each refactor, record:

*   clean build time
*   incremental build time
*   `cargo check` time
*   proc-macro contribution
*   codegen time
*   binary size
*   expanded code size
*   readability impact
*   maintainability impact

# 19. Recommended Architecture for Low-Fan-out CubeCL Code

A practical low-fan-out CubeCL architecture usually has:

1.  **One public launchable kernel per real algorithm entry point**
2.  **A small set of meaningful free `#[cube]` helper functions**
3.  **Generic numeric abstraction using `Float`, `Int`, or `Numeric`**
4.  **`#[define]` for launch-time type selection**
5.  **`#[comptime]` and `comptime!` for constants and policies**
6.  **Minimal use of `#[cube]` traits and impl blocks**
7.  **Derive macros only on true CubeCL boundary types**
8.  **Debug expansion enabled only when needed**
9.  **Only necessary backend features enabled**
10. **Macro-heavy code isolated in dedicated crates**

The target state is:

```text
During Rust build:
  Few generic expand functions
  Few launch wrappers
  Limited monomorphization
  Smaller generated Rust code
  Smaller LLVM IR

During CubeCL JIT:
  Inject tile sizes, shapes, and policies through comptime
  Resolve actual element types through context / #[define]
  Generate only the needed GPU kernel variants
```

# 20. Common Anti-patterns and Fixes

## Anti-pattern 1: Every Helper Is Launchable

Avoid:

```rust
#[cube(launch)] fn helper_a(...) { ... }
#[cube(launch)] fn helper_b(...) { ... }
#[cube(launch)] fn helper_c(...) { ... }
```

Fix:

```text
Only the real host entry point should be #[cube(launch)].
Internal helpers should be plain #[cube].
```

***

## Anti-pattern 2: Trait-driven CubeCL Everywhere

Avoid:

```rust
#[cube]
trait Op<...> {
    // ...
}

#[cube]
impl<...> Op<...> for SomeType {
    // ...
}
```

Fix:

```text
Use free #[cube] helper functions unless trait abstraction is essential.
```

***

## Anti-pattern 3: One Kernel per Numeric Type

Avoid:

```rust
kernel_f16(...)
kernel_bf16(...)
kernel_f32(...)
kernel_f64(...)
```

Fix:

```rust
#[cube]
fn kernel<F: Float>(...) {
    // shared algorithm
}
```

Use `#[define]` if the host needs launch-time type selection.

***

## Anti-pattern 4: Runtime IR for Compile-time Policy

Avoid representing compile-time-only policy as runtime IR values.

Fix:

```rust
#[cube(launch)]
fn kernel<F: Float>(
    ...,
    #[comptime] use_relu: bool,
) {
    if comptime!(use_relu) {
        // generate relu path
    }
}
```

***

## Anti-pattern 5: Derive Macros on Internal Types

Avoid:

```rust
#[derive(CubeType, CubeLaunch)]
struct InternalTemporaryState {
    // ...
}
```

Fix:

```text
Only derive CubeType / CubeLaunch for true CubeCL-visible boundary types.
```

***

## Anti-pattern 6: Building All Backends During Development

Avoid:

```bash
cargo build --all-features
```

Prefer:

```bash
cargo build --no-default-features --features wgpu
```

or whichever backend is actually needed.

***

# 21. Refactoring Checklist

## Launch Surface

*   [ ] Is every `#[cube(launch)]` function actually launched from the host?
*   [ ] Can any launch kernel be downgraded to plain `#[cube]`?
*   [ ] Are similar launch kernels mergeable with `#[comptime]`?

## Traits and Impl Blocks

*   [ ] Are `#[cube]` traits necessary?
*   [ ] Could a free helper function replace a trait method?
*   [ ] Are impl blocks expanded only where the abstraction is valuable?

## Numeric Specialization

*   [ ] Are there separate kernels for `f16`, `bf16`, `f32`, or `f64`?
*   [ ] Can they become one `F: Float` kernel?
*   [ ] Can host-side type selection move to `#[define]`?

## Const Generics and Policies

*   [ ] Are tile sizes encoded as types or associated constants?
*   [ ] Can they become `#[comptime]` arguments?
*   [ ] Are policy flags represented as runtime IR unnecessarily?

## Helper Functions

*   [ ] Are there too many tiny `#[cube]` helpers?
*   [ ] Are helpers meaningful algorithmic stages?
*   [ ] Should some small helpers be inlined?

## Derives

*   [ ] Is `CubeType` derived only for CubeCL-visible data?
*   [ ] Is `CubeLaunch` derived only for launch boundary types?
*   [ ] Are host-only structs free from CubeCL derives?

## Debug

*   [ ] Are debug symbols enabled by default?
*   [ ] Can debug expansion be opt-in?

## Cargo and Workspace

*   [ ] Are unnecessary backend features disabled?
*   [ ] Is CubeCL-heavy code isolated in a separate crate?
*   [ ] Are dev/test profiles lightweight?
*   [ ] Is CI split by backend where appropriate?

***

# 22. Decision Guide

## Should this function be `#[cube(launch)]`?

Use `#[cube(launch)]` only if it must be directly launched from the host.

Otherwise, use plain `#[cube]`.

***

## Should this abstraction be a `#[cube]` trait?

Use a CubeCL trait only if the abstraction is essential inside kernel code.

If a free function works, prefer the free function.

***

## Should this be split by numeric type?

Only split by numeric type if the algorithm is materially different.

If the structure is the same, use a generic numeric kernel.

***

## Should this value be runtime or compile-time?

If it affects specialization or IR generation and is fixed at kernel compile time, use `#[comptime]` or `comptime!`.

***

## Should this type derive `CubeType` or `CubeLaunch`?

Only if it is a true CubeCL-visible boundary type.

***

# 23. Final Recommendation

The highest-leverage rule is:

> **Minimize the number of launchable kernels and keep the rest of the kernel graph small, generic, and function-based.**

Then apply the supporting techniques:

*   use `#[cube(launch)]` only for true entry kernels
*   use plain `#[cube]` for internal helpers
*   prefer free functions over broad trait/impl expansion
*   use generic numeric kernels instead of per-type duplication
*   use `#[define]` for launch-time type selection
*   use `#[comptime]` and `comptime!` for constants and policies
*   derive `CubeType` and `CubeLaunch` only on boundary types
*   avoid excessive backend feature combinations
*   isolate CubeCL-heavy code in dedicated crates
*   measure with `cargo build --timings`, `cargo expand`, and `-Zmacro-stats`

The overall goal is not merely to make Rust code “faster,” but to make Rust generate and compile **less code**.

CubeCL is a JIT-oriented system, so many variations do not need to be embedded into the Rust binary ahead of time. Let Rust compile a small number of generic expansion paths, and let CubeCL specialize kernels at JIT time.
