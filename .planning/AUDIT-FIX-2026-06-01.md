### F-13 detail

The `String`/`FilePath` atom forms previously returned `NotYetImplemented` for Z-matrix
input. The old per-line `tokens < 4` guard could not even detect a Z-matrix block (the 3rd
atom onward has ≥ 5 tokens and was misread as Cartesian).

Resolution — faithful port of upstream `pyscf/gto/mole.py::from_zmatrix`
(+ `pyscf.symm.geom::rotation_mat`), Apache-2.0:

- **Block-level format detection** matching upstream exactly: after stripping blank/comment
  lines, a first atom line with `< 4` whitespace tokens selects the Z-matrix path; otherwise
  Cartesian (unchanged behaviour).
- **Per-line construction** selected by token count (origin → +x bond → bond+angle →
  bond+angle+dihedral), with the Rodrigues axis-angle rotation matrix and the
  colinear-dihedral fallback reproduced verbatim.
- **Unit/origin/axes** post-processing reuses the existing Cartesian path, as upstream does.

**Verification**

- Pinned to PySCF's published output via the `from_zmatrix` docstring oracle (4-H example,
  byte-identity to 1e-6).
- 6 tests total: docstring oracle, water internals (bond lengths + H–O–H angle), Cartesian
  path regression, `;` separator, Angstrom→Bohr unit conversion, out-of-range reference
  rejection.
- Full `pyscf-gto` suite green: 59 lib tests + integration tests, 0 failures.

**Gates**

- `cargo +nightly test -p pyscf-gto --locked` → exit 0.
  - Nightly required: the workspace manifest does not parse on stable because
    `pyscf-dft → libxc_rs` uses the `profile-rustflags` Cargo feature. `pyscf-gto` does **not**
    pull `libxc` into its dep graph, so the ~6h libxc build was **not** triggered.
- `rustfmt --edition 2024 --check` → clean.
- `cargo +nightly clippy -p pyscf-gto` → no findings for the new code (remaining warnings are
  pre-existing cintx-dependency noise).

**Intentional deviation:** PySCF's `eval()` expression path (`DISABLE_EVAL=false`) is not
supported — Z-matrix coordinates must be plain numbers (equivalent to upstream
`DISABLE_EVAL=True`).

### F-10 detail

`init_guess_by_chkfile` returned `NotYetImplemented` when the prior chkfile's basis differed
from the current basis (`prior.nao != current nao`). Resolution — faithful port of
`project_mo_nr2nr` (`pyscf/scf/addons.py`):

```text
C2 = S22⁻¹ · (S21 · C1),   S22 = <cur|cur> = int1e_ovlp(cur),
                           S21 = <cur|prior> = intor_cross(cur, prior)
```

then `D[μν] = Σ_i occ_i·C2[μ,i]·C2[ν,i]`. The prior Mole/basis is reconstructed from the `mol`
JSON already stored in the chkfile (new `chkfile::load_mol_json_from_file` +
`pyscf_gto::loads`). The layout/solve idiom mirrors `init_guess_by_minao` (itself
`project_mo_nr2nr(ano, I, mol)`): F-order overlaps in `IntorOutput.values`, per-column
`solve_linear` against S22, `oracle_sum` density reduction. The byte-verified same-basis fast
path is preserved (extracted to `density_from_mos`).

**Verification scope** (in-sandbox, no live PySCF):
- **Same-basis identity invariant** (rigorous anchor): projecting onto the same basis yields
  `C2 == C1`, so the projected density equals the direct same-basis RDM1 — exercises the full
  `S21·C1` contraction + per-column S22 solve and proves it collapses to identity.
- **E2E cross-basis** (sto-3g → 6-31g) through the real chkfile read + `loads` path: seed shaped
  to the current basis, finite, symmetric.
- **Graceful error** when the stored prior mol cannot be reconstructed.
- **Residual risk:** exact cross-basis numbers are NOT oracle-verified against upstream
  in-sandbox. The `intor_cross` machinery itself is byte-verified via the default minao guess.

**Gates:** `cargo +nightly test -p pyscf-scf --locked` → exit 0 (5 chkfile/projection tests +
full suite green; SCF dep graph excludes libxc). `rustfmt --edition 2024 --check` → clean.
`cargo +nightly clippy -p pyscf-scf` → no findings for the new code.
