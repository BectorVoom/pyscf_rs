### F-02 detail (follow-up pass — 2026-06-01)

Originally classified manual-only ("needs cart `ao_loc`/`nao` kernel surface —
architectural change"). The architectural concern turned out to be modest:

- The cartesian `ao_loc`/`nao` is the **same `make_loc` formula** `make_env`
  already applies (`((l+1)(l+2)/2)·nctr` per shell) — built fresh from `_bas` in
  the wrapper, independent of `mol.cart`, mirroring upstream
  `make_loc(bas, 'GTOval_cart_deriv1')`.
- The deriv1 host kernel already computes the cartesian values/gradients
  **before** applying the c2s transform. Cartesian output = those pre-transform
  values, so no new numeric stencil is needed.

Resolution:
- `pyscf-kernels` (`eval_gto.rs`): `eval_gto_sph_deriv1_cpu` gains a `spherical`
  flag; when `false` it writes the `ncart(l)` cartesian components directly (no
  c2s) at the cartesian `ao_loc` offsets. New `pub eval_gto_cart_deriv1`
  (host-only — the device deriv1 launcher emits spherical AOs). No `l` ceiling on
  the cart path (never calls `c2s_coeff`).
- `pyscf-gto` (`eval_gto.rs`): route `GTOval_cart_deriv1` (build cart loc, call
  the new kernel, shape `[4,ngrids,nao_cart]`) and `GTOval_ip_cart`
  (= `cart_deriv1[1:4]`, slice off the value block → `[3,ngrids,nao_cart]`).

This also closes the **`GTOval_ip_cart` arm of F-01** (the only remaining
cartesian gradient gap there).

**Verification** (in-sandbox, no live PySCF):
- **Congruence oracle** (`tests/eval_gto_cart_deriv1_oracle.rs`):
  `c2s(GTOval_cart_deriv1) == GTOval_sph_deriv1` (all 4 components, `<1e-10`) on
  H2O/cc-pVDZ (s,p,d — exercises l=2 where `ncart=6 ≠ nsph=5`). The spherical
  side is itself byte-verified against an independent longhand reference
  (`eval_gto_deriv1_oracle.rs`), so equality transitively pins the cartesian
  output. Device-sph vs host-cart is also a cross-implementation check.
- **Finite-difference** check on the cart gradient (independent of c2s *and* the
  analytic-derivative algebra).
- `GTOval_ip_cart == GTOval_cart_deriv1[1:4]` bit-for-bit.
- Replaces the stale `deriv1_cart_returns_not_yet_implemented_phase_4` smoke test.

**Still deferred:** `GTOval_*_deriv2` (no deriv2 kernel exists — `GTOval_sph_deriv2`
is itself NYI); `GTOval_ig*` (distinct GIAO kernel). **Residual risk:** absolute
cartesian numbers are congruence-/FD-verified in-tree, not live-PySCF-oracle-
verified.

**Gates:** `cargo +nightly test -p pyscf-gto` + `-p pyscf-kernels --locked` → full
suites green; `rustfmt --check` clean; clippy no findings on new code.

### F-04 detail (follow-up pass 2026-06-01)

Originally classified *not-a-bug* on the assumption that arity-3 always needs a
distinct auxiliary basis. That was wrong: upstream `mol.intor('int3c2e_sph')`
called with no auxmol is a legitimate operation — all three centers range over
`mol`'s own basis, yielding `[nao, nao, nao]`. The dispatcher returned
`NotYetImplemented{phase:3}` for it.

Resolution — `evaluate_arity3_single_mol` (`crates/pyscf-gto/src/intor.rs`): the
`auxmol == mol` specialisation of the byte-verified `evaluate_int3c2e_with_auxmol`.
It iterates every shell triple `(i,j,k)` over mol's own cintx `BasisSet` and
stitches the per-triple F-order `[ni,nj,nk]` block into a global F-order
`[nao,nao,nao]` buffer, using the same `OperatorId`/`SessionRequest` path the DF
wrapper uses (so it inherits libcint byte-identity at the cintx source). Scalar
arity-3 only; component-leading arity-3 derivatives (`int3c2e_ip1` …) stay
`NotYetImplemented` (grad-path, cintx-gated — F-01/F-08).

**Verification** (in-sandbox, no live PySCF):
- **Rigorous in-tree oracle** (`tests/int3c2e_auxmol.rs::int3c2e_single_mol_equals_self_auxmol`):
  `intor(mol, "int3c2e_sph")` is bit-identical (`<1e-12`) to
  `intor_with_auxmol(mol, "int3c2e_sph", mol)` — the latter is itself
  libcint-byte-verified at the cintx source, so equality pins the single-mol
  path to the same numbers. Shape `[nao,nao,nao]`, finite, non-zero asserted.

**Gates:** `cargo +nightly test -p pyscf-gto --locked` → full suite green (new
oracle test passes; pyscf-gto dep graph excludes libxc, no ~6h build).
`rustfmt --edition 2024 --check` → clean. `cargo +nightly clippy -p pyscf-gto`
→ no findings on the new code.

### F-13 detail

input. The old per-line `tokens < 4` guard could not even detect a Z-matrix block (the 3rd
atom onward has ≥ 5 tokens and was misread as Cartesian).

Resolution — faithful port of upstream `pyscf/gto/mole.py::from_zmatrix`
(+ `pyscf.symm.geom::rotation_mat`), Apache-2.0:

- **Block-level format detection** matching upstream exactly: after stripping blank/comment
  lines, a first atom line with `< 4` whitespace tokens selects the Z-matrix path; otherwise
  Cartesian (unchanged behaviour).
- **Per-line construction** selected by token count (origin → +x bond → bond+angle →
  bond+angle+dihedral), with the Rodrigues axis-angle rotation matrix and the
  colinear-dihedral fallback reproduced verbatim.
- **Unit/origin/axes** post-processing reuses the existing Cartesian path, as upstream does.

**Verification**

  byte-identity to 1e-6).
- 6 tests total: docstring oracle, water internals (bond lengths + H–O–H angle), Cartesian
  path regression, `;` separator, Angstrom→Bohr unit conversion, out-of-range reference
  rejection.
- Full `pyscf-gto` suite green: 59 lib tests + integration tests, 0 failures.

  - Nightly required: the workspace manifest does not parse on stable because

### F-10 detail

`init_guess_by_chkfile` returned `NotYetImplemented` when the prior chkfile's basis differed
from the current basis (`prior.nao != current nao`). Resolution — faithful port of
`project_mo_nr2nr` (`pyscf/scf/addons.py`):

```text
C2 = S22⁻¹ · (S21 · C1),   S22 = <cur|cur> = int1e_ovlp(cur),
                           S21 = <cur|prior> = intor_cross(cur, prior)
```

then `D[μν] = Σ_i occ_i·C2[μ,i]·C2[ν,i]`. The prior Mole/basis is reconstructed from the `mol`
JSON already stored in the chkfile (new `chkfile::load_mol_json_from_file` +
`pyscf_gto::loads`). The layout/solve idiom mirrors `init_guess_by_minao` (itself
`project_mo_nr2nr(ano, I, mol)`): F-order overlaps in `IntorOutput.values`, per-column
`solve_linear` against S22, `oracle_sum` density reduction. The byte-verified same-basis fast
path is preserved (extracted to `density_from_mos`).

**Verification scope** (in-sandbox, no live PySCF):
- **Same-basis identity invariant** (rigorous anchor): projecting onto the same basis yields
  `C2 == C1`, so the projected density equals the direct same-basis RDM1 — exercises the full
  `S21·C1` contraction + per-column S22 solve and proves it collapses to identity.
- **E2E cross-basis** (sto-3g → 6-31g) through the real chkfile read + `loads` path: seed shaped
  to the current basis, finite, symmetric.
- **Graceful error** when the stored prior mol cannot be reconstructed.
- **Residual risk:** exact cross-basis numbers are NOT oracle-verified against upstream
  in-sandbox. The `intor_cross` machinery itself is byte-verified via the default minao guess.

**Gates:** `cargo +nightly test -p pyscf-scf --locked` → exit 0 (5 chkfile/projection tests +
full suite green; SCF dep graph excludes libxc). `rustfmt --edition 2024 --check` → clean.
`cargo +nightly clippy -p pyscf-scf` → no findings for the new code.
