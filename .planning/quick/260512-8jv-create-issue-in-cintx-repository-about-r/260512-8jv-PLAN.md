# Quick Task 260512-8jv: Create issue in cintx repository about remaining Phase 2 tasks

## Context

pyscf_rs Phase 2 (GTO) verification passed 11/11 must-haves with a small set of items
explicitly tracked as **deferred-to-cintx-workstream** per Phase 2 design decision D-06
(parallel sequencing). Phase 2 verification report:
`.planning/phases/02-gto/02-VERIFICATION.md` (status: passed, 2026-05-11).

The deferred items are concrete asks against the sibling `cintx` repository:

1. **ECP operator family (`int1e_ecp_*` — Type-1 Coulomb-like + Type-2 spin-orbit-like projectors).**
   Phase 2 ships ECP **loading** (`format_ecp` + `make_ecp_env` + `EcpEngine` trait +
   `EcpEngineNotAvailable` stub), but **evaluation** is gated on cintx merging
   `cint1e_ecp_*` operators. pyscf_rs plan `02-10-PLAN.md` is a placeholder gap-closure
   plan with `status: PENDING_CINTX_ECP_MERGE` that swaps the stub for a cintx-backed
   `CintxEcpEngine` once cintx ships.

   Verify: `grep -l int1e_ecp ~/Documents/workspace/cintx/crates/*/src/*.rs` returns
   nothing (confirmed 2026-05-11).

2. **Arity ≥3 `SessionRequest` dispatch in the `cintx-rs` safe API.**
   `cintx-ops`'s manifest catalogs the arity-3/4 operators (`int2e`, `int3c2e`,
   `int3c2e_ip1`, `int4c1e`, plus the `_sph` / `_cart` / `_spinor` variants), but
   `cintx-rs::SessionRequest::evaluate` does not yet dispatch them. pyscf_rs's
   `crates/pyscf-gto/src/intor.rs:170-189` returns `NotYetImplemented{phase:2}` for
   any arity 3/4 name, and `tests/oracle/test_intor_oracle.py::test_intor_arity_ge3_deferred`
   is marked xfail. This blocks downstream pyscf_rs work: plan 03-05 (DF-HF) needs
   `int3c2e`, Phase 7 (gradients) needs `int3c2e_ip1`.

3. **Real-integral evaluation in the safe API.**
   `cintx-rs::api.rs:465 fn fill_staging_values` populates output with a synthetic
   pattern (`((idx + 1) as f64) * 0.5` for `spheric`) rather than dispatching to
   `cintx-compat::raw::eval_raw`. pyscf_rs plan 02-01 W0-T1 noted this as a
   forward-looking concern: "the safe API will need to flip onto real-integral
   evaluation before 02-05 lands the user-facing `mol.intor(name)` over real
   shell-pair iteration." pyscf_rs has worked around by stitching `cintx-compat::raw`
   under the safe-API descriptor in `intor.rs:170`, but byte-identity vs upstream
   PySCF for `mol.intor('int1e_ovlp_sph')` is gated by this flip.
