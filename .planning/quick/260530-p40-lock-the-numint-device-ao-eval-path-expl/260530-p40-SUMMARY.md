# Phase quick-260530-p40 Plan 01: Lock the numint device AO-eval path Summary

One-liner: Added an always-on lock test pinning that DFT's numint AO evaluation runs through the device `eval_gto` kernel path (value + deriv1) correctly, and documented that `eval_rho`'s ρ=AOᵀ·D·AO contraction stays host by design (FOUND-06) — no production code changed.

## What was done

### T1 — Lock test `crates/pyscf-dft/tests/numint_device_ao_path.rs` (new, always-on, default features)
Builds H2O/cc-pVDZ via the `M(MoleBuildArgs{atom:"O 0 0 0; H 0 0 0.96; H 0 0.93 -0.24", basis:"cc-pvdz", unit:Ang})` pattern (`nao_nr = 24`, maxl = 2 → s/p/d → exercises the general l ≥ 1 device `eval_gto` kernel). Grid = 8 hand-listed coords near the three atoms (no `Grids::build()` needed). `PYSCF_BACKEND` unset → `select_backend` resolves the `CpuRuntime` `#[cube]` device kernel.

## (1) Exact assertions implemented + observed diffs

- **Assertion A (PRIMARY — eval_rho over device AO block):** `ao = pyscf_gto::eval_gto(&mol,"GTOval_sph",&coords).values` (F-order `[ngrids,nao]`, len 8·24 = 192) → `NumInt::eval_rho(&ao, &dm, ngrids, XcType::Lda)` → `assert grad.is_none()` → compared elementwise against an **independent hand-written triple sum** `want[g] = Σ_μ Σ_ν ao[g+μ·ngrids]·D[μν]·ao[g+ν·ngrids]` (plain nested f64 loop in the test; shares no code with `oracle_sum`). Tolerance `|ρ[g] − want[g]| < 1e-9`. **Observed:** PASS for all 8 grid points (ordering Δ vs the pairwise tree well under tol; bounded correctness, not bit-identity).
- **Assertion B (cross-kernel value self-consistency):** `ao1 = pyscf_gto::eval_gto(&mol,"GTOval_sph_deriv1",&coords).values` (`[4,ngrids,nao]`, len 4·8·24 = 768); its comp-0 slice `ao1[0..ngrids*nao]` compared elementwise to the `GTOval_sph` block `ao`. Tolerance `< 1e-12`. **Observed:** PASS for all 192 elements (the value-only and 4-component device kernels agree on the value numerics; both are independent `#[cube]` kernels).

## (3) ROCm variant: NOT added (and why)
A `#[cfg(feature = "rocm")]` sibling was dropped: pyscf-dft declares no `rocm` feature (only `default`, `libxc`, `python`), so gating on it emits an `unexpected_cfgs` warning — not a clean addition. A NOTE comment in the test records this and that the always-on default-backend test already drives the device kernel path; selecting a physical device backend is an env (`PYSCF_BACKEND`) concern over the same public `eval_gto` surface, covered by pyscf-gto/pyscf-kernels device tests.

## (4) dm + coords used
- **dm:** fixed deterministic symmetric `Density{nao:24, data}` where `D[μν] = 0.5 + 0.3·((7μ+3ν)%11)/11 − 0.15·((5μ+ν)%13)/13`, then symmetrized `D=(D+Dᵀ)/2`. NO SCF run — a pure algebra fixture.
- **coords (8 pts):** `[0.05,0.05,0.05]` (near O), `[0,0,0.96]` (H1), `[0,0.93,-0.24]` (H2), `[0.1,-0.1,0.2]`, `[0,0,0.5]`, `[0,0.45,-0.1]`, `[-0.2,0.3,0.4]`, `[0.3,0.3,0.3]` — all near nuclei so AO values are nonzero (non-degenerate lock).

## Phase-8 GPU-enable closure note
This is the FINAL Phase-8 GPU-enable slice. The device `eval_gto` surface (value + l ≥ 1 + deriv1; Phase-8 ljv/mlg/oms kernels) is complete, and numint inherits it transparently via `eval_gto_block → pyscf_gto::eval_gto → select_backend`. The remaining GPU work — a GPU `eval_rho` — is an **explicitly deferred perf item** per the user's keep-`eval_rho`-host decision: it would be tolerance-bounded (~1e-9) rather than bit-identical and must not land without an explicit SCF-bit-exactness decision (FOUND-06).
