# Quick Task 260522-b06: implement f32/f64 precision switching using generics - Context

**Gathered:** 2026-05-21
**Status:** Ready for planning

<domain>
## Task Boundary

Make pyscf-rs generic over floating-point precision (f32 / f64) using Rust
generics, so the same code can run in single or double precision. f64 remains
the default (preserves bit-exact PySCF parity); f32 is an explicit opt-in for
speed / GPU. Driven by the user request: "implement function of switching f32
or f64. Please use generics."
</domain>

<decisions>
## Implementation Decisions (locked via AskUserQuestion 2026-05-21)

### Scope
- **All active compute crates.** Thread the precision generic through:
  `pyscf-core`, `pyscf-algebra`, `pyscf-gto`, `pyscf-scf`, `pyscf-df`,
  `pyscf-diis` (and the supporting `pyscf-runtime` / `pyscf-kernels` layers as
  needed to keep the algebra-wall intact).
- **Out of scope for this task:** `pyscf-py` (PyO3/NumPy boundary stays f64 via
  the default type param), and the empty stub crates `pyscf-dft`, `pyscf-mp2`,
  `pyscf-ccsd`, `pyscf-grad`, `pyscf-geomopt`.
- This is larger than a normal quick task (the user chose it deliberately over a
  smaller foundation-only slice). Plan must be dependency-ordered and atomic so
  it can be paused/resumed and so each crate layer compiles independently.

### Mechanism
- **Generic `<T: Scalar>` with `f64` as the default type parameter.**
- Define a `Scalar` trait. It must live in `pyscf-core` (the cubecl-free leaf
  crate that every other crate depends on) and bound ONLY on host-side traits
  (e.g. `num_traits::Float + Copy + Send + Sync + bytemuck::Pod + 'static` plus
  the consts/ops actually needed). It MUST NOT require `cubecl::Float`, or that
  would drag cubecl across the algebra-wall into method crates.
- The `cubecl::Float` / device-element bound is added only inside
  `pyscf-algebra` / `pyscf-kernels` (the crates the wall permits to name
  cubecl), e.g. via a sealed extension or an added bound at the Tensor/kernel
  layer.
- Default type param (`= f64`) keeps existing call sites and parity tests
  compiling unchanged.

### Default / parity
- **f64 is the default; f32 is opt-in.** Do not change any default that would
  break existing oracle/regression bit-exact tests.

### Claude's Discretion
- Exact trait name (`Scalar` vs `Float` vs `Real`), whether to add a thin
  `pyscf-numeric` leaf crate vs putting the trait in `pyscf-core`, and the exact
  task decomposition — left to the planner, subject to the constraints above.
</decisions>

<canonical_refs>
## Architectural constraints (verified in codebase 2026-05-21)

- **Algebra-wall (D-04 / D-05 / ALG-06):** ONLY `pyscf-algebra` and
  `pyscf-runtime` may name `cubecl::*` types. Method crates (`pyscf-gto`,
  `pyscf-scf`, `pyscf-dft`, `pyscf-df`, `pyscf-diis`) consume `Tensor` only.
  Enforced by `xtask check-dependency-wall`. The `Scalar` generic must not
  violate this.
- **Existing runtime model:** `pyscf-runtime` already defines a `DType` enum
  that `Tensor` carries (re-exported as `pyscf_algebra::DType`). The new
  compile-time generic complements, not replaces, this runtime tag — planner
  should reconcile the two explicitly.
- **Dependency DAG (active crates):**
  `core` (leaf, no cubecl) → `runtime` → `algebra` (cubecl + faer + Tensor) →
  `kernels` → {`gto`, `diis`, `df`} → `scf` (top).
- **`num-traits` is NOT yet a dependency** — must be added at workspace level +
  to `pyscf-core`. `bytemuck` is already a workspace dep.
- **f64 token counts (active crates):** scf 96, gto 66, algebra 51, diis 26,
  chkfile 24, df 17, core 33, kernels 11, runtime 8.

## COMPILE-TIME GUARDRAILS (hard constraints)

- **NEVER build `pyscf-dft`** or anything that pulls `libxc_rs` into the dep
  graph — it triggers a ~6h libxc compile (`libxc_rs` patch is intentionally
  disabled in root Cargo.toml). Verification must target specific crates with
  `cargo check -p <crate>`, never `cargo build`/`cargo test --workspace`.
- **Avoid freezing compile:** blanket `<T>` monomorphization across the whole
  workspace doubles instantiations. Keep `f64` the default so the normal build
  only monomorphizes f64; exercise the f32 path through a narrow, explicit
  smoke test rather than instantiating f32 everywhere by default.
</canonical_refs>
