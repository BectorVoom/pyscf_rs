# Quick Task 260522-b06: f32/f64 Precision Switching via Generics Summary

**Two-tier precision generic — a cubecl-free host-only `Scalar` trait in pyscf-core plus an in-wall `DeviceScalar: Scalar + cubecl::Float` — threaded bottom-up so `Tensor<T = f64>` is generic over precision while f64 stays the default and only-monomorphized type, with the algebra-wall (ALG-06) intact.**

- **Duration:** ~25 min

- **Code files changed:** 11 (4 created, 7 modified)

## Accomplishments

- Added a host-only, sealed `Scalar` trait in pyscf-core (`num_traits::Float + Copy + Send + Sync + bytemuck::Pod + 'static`) with NO cubecl bound, plus `KIND: ScalarKind` and `NAME` consts for f32/f64 — the cubecl-free leaf of the precision stack.
- Made `Tensor` generic as `Tensor<T: Scalar = f64>`: bare `Tensor` still means `Tensor<f64>`, so every existing f64 call site (algebra primitives + all method crates) compiles unchanged. The runtime `DType` tag is retained but now derived from `T` via `dtype_of::<T>()`, so the compile-time element type and runtime tag can never disagree.
- Confined the `cubecl::Float` device bound to inside the wall via `DeviceScalar` (pyscf-algebra) + a re-export and `KernelScalar = f64` seam (pyscf-kernels). `check-dependency-wall` passes — no cubecl name leaked into any method crate.
- Verified gto/diis/df/scf all `cargo check` clean against the generic Tensor under the f64 default with zero source edits (no Tensor constructor signatures were hit in method crates).
- Added one narrow f32 smoke test proving Tensor instantiates at f32 (DType::F32 / elem_size 4 / nbytes 64), the default param resolves to f64, and generic host Scalar arithmetic works at f32 — the only place f32 is forced through the surface.

## Decisions Made

- **T -> DType reconciliation lives in pyscf-algebra, not pyscf-core.** pyscf-core is a lower leaf with no `pyscf-runtime` dependency, so it cannot name `DType`. pyscf-core carries a local `ScalarKind` enum; pyscf-algebra (the lowest crate depending on both core and runtime) maps `ScalarKind -> DType` via `dtype_of`. Followed the plan's prescribed approach exactly.
- **`DeviceScalar` bound on `cubecl::prelude::Float`.** Confirmed (by inspecting cubecl-core 0.10.0 source) that `cubecl::prelude` re-exports `frontend::*` which contains `Float`, making `cubecl::prelude::Float` a definitely-valid path; the eval_gto kernel already uses `cubecl::prelude::*`.
- **Kernels stay f64.** Did not generalize the `eval_gto` cubecl kernel — generalizing now would double cubecl monomorphization for zero current call site (a compile-time blowup with no payoff), violating the avoid-blowup constraint.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `dtype_of` wildcard arm required by `#[non_exhaustive]` ScalarKind**
- **Found during:** Task 2 (generic Tensor + DeviceScalar)
- **Issue:** `ScalarKind` is `#[non_exhaustive]` (deliberately, to reserve f16/bf16). A cross-crate `match T::KIND` in `dtype_of` therefore failed to compile (E0004: non-exhaustive patterns, `_` not covered).
- **Fix:** Added a `_ => DType::F64` wildcard arm with a comment noting it falls back to the chemistry-safe F64 default until a new precision lands in both `ScalarKind` and `DType`.
- **Files modified:** `crates/pyscf-algebra/src/scalar.rs`
- **Verification:** `cargo check -p pyscf-algebra` clean; `dtype_of` unit test asserts F32/F64 mapping.
- **Committed in:** `cb01f47` (Task 2 commit)

**2. [Rule 3 - Blocking] Default-type-param test needed a type annotation**
- **Found during:** Task 2 (generic Tensor + DeviceScalar)
- **Issue:** The plan asked the default-param test to call `Tensor::placeholder(vec![1])` with no turbofish. A bare unannotated associated-function call cannot infer `T` (E0283: type annotations needed) — a struct default type param only applies when the result type is otherwise determined.
- **Fix:** Annotated the binding as `let t: Tensor = Tensor::placeholder(...)`. Bare `Tensor` (the annotation) resolves to `Tensor<f64>` via the default param — which is precisely the property under test, and mirrors how the algebra primitives' `&Tensor` parameter types pick up the default.
- **Files modified:** `crates/pyscf-algebra/src/tensor.rs` (unit test) and the same shape used in `crates/pyscf-algebra/tests/f32_smoke.rs`
- **Verification:** `cargo test -p pyscf-algebra tensor` and `--test f32_smoke` both pass; `default_type_param_resolves_to_f64` and `bare_tensor_resolves_to_f64_default` assert `dtype == DType::F64`.
- **Committed in:** `cb01f47` (Task 2) and `4c6ab55` (Task 6)

**3. [Rule 3 - Blocking] Removed now-unused `DType` import in backend_matrix.rs**
- **Found during:** Task 2
- **Issue:** Updating the in-crate `placeholder(shape, dtype)` call sites to the new one-arg form left `use pyscf_runtime::DType;` unused in `backend_matrix.rs`.
- **Fix:** Dropped the dead import. (Updating these 3 in-crate test call sites was itself the anticipated "more call sites changed than expected, fix within Task 2 scope" — they are the only `placeholder(shape, dtype)` sites in the workspace and all live inside pyscf-algebra.)
- **Files modified:** `crates/pyscf-algebra/tests/backend_matrix.rs`
- **Verification:** `cargo test -p pyscf-algebra tensor` builds backend_matrix clean (no unused-import warning).
- **Committed in:** `cb01f47` (Task 2 commit)
