## What changed (commit `250670c`)

The atomic RHF is always spherical (`atom_hf.rs:114`), so for a cartesian
molecule the per-atom density is in spherical AO count and needs a molecular
sph→cart projection — the upstream `Mole.cart2sph_coeff` + `hf.py:528-531`
`cart2sph`/`atcart2sph` branch.

- **pyscf-kernels:** `pub fn cart2sph_l_matrix(l)` — exposes the per-`l` libcint
  `g_trans_cart2sph` matrix (the same one `eval_gto_sph` uses) so higher crates
  can assemble the molecular coefficient.
- **pyscf-gto:** `cart2sph_coeff(mol) -> (C [nao_cart × nao_sph] row-major,
  nao_sph)` — block-diagonal per shell-contraction; `C[cart,sph] =
  c2s_coeff[sph,cart]` (the transpose relationship, empirically confirmed vs
  PySCF). New module `cart2sph.rs`.
- **pyscf-scf:** both cart branches now build a **spherical sibling** Mole
  (`clone`, `cart=false`, `Mole::build()` via the **F-11 IoC hook** shipped in
  260601-tyg), run the already-validated spherical guess to get `D_sph`, then
  project `D_cart = C·D_sph·Cᵀ` (`oracle_sum` reductions, T-03-14-NUM). The
  spherical path is byte-unchanged.

## Verification

- **Byte-exact vs live PySCF 2.12.1** (the genuinely-new numeric kernel): the
  full molecular `cart2sph_coeff` for H2O/cc-pVDZ cart `[25,24]` matches
  `mol.cart2sph_coeff(normalized='sp')` to **max |Δ| = 2.2e-16** (machine eps).
  This was first proven on the O d-block (element-for-element) to ground the
  transpose-relationship before coding.
- **End-to-end invariant:** `Tr(D_cart·S_cart) = nelec` (atol 1e-9) for **both**
  `atom` and `huckel` guesses on H2O/cc-pVDZ cart (a d-shell molecule — the first
  place cart≠sph, `nao_cart=25 > nao_sph=24`). A wrong projection breaks this.
  New tests in `crates/pyscf-scf/tests/init_guess_atom_huckel.rs` (2).
- **Regression:** full `pyscf-kernels` + `pyscf-gto` + `pyscf-scf` test suites
  green (incl. the spherical `atom`/`huckel` mode-independence gate). `cargo
  +nightly`; `pyscf-scf` dep graph has 0 libxc rows — no ~6h build triggered.

## Documented limitation (not a regression)

The spherical-sibling rebuild reuses the **F-11 `Mole::build()` Name-basis echo
round-trip**, so the cart branch supports `Name`-form bases (the common case,
incl. cc-pVDZ / 6-31G*-style). Programmatic/parsed/text bases still build via
`pyscf_gto::M`. Consistent with the F-11 disposition.
