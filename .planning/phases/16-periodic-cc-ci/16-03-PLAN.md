<objective>
Four Phase-16 plans (16-09, 16-10, 16-11, 16-13) are dead without an iterative
non-symmetric Davidson, and `PBC-MASTER-PLAN §8.8` costs it at **zero**:

```
pyscf/pbc/cc/eom_kccsd_ghf.py:128    eig = lib.davidson_nosym1
pyscf/pbc/cc/eom_kccsd_ghf.py:1352   eig = lib.davidson_nosym1
pyscf/pbc/ci/kcis_rhf.py:97          eig = lib.davidson_nosym1
```

`grep -rn "davidson" crates/ -i` returns only "McMurchie–Davidson" — a
different Davidson entirely. `pyscf-algebra` exposes `eigh_gen`, which is
**symmetric**, and 17-02 added a direct `faer` `Eigen::new_from_real` for a
**dense** general complex eigenproblem. Neither is this.

Port `pyscf/lib/linalg_helper.py:741` `davidson_nosym1` and its default
`pick_real_eigs`. This is a self-contained numerical-methods plan with no PBC
dependency and no PySCF oracle requirement, which is why it is wave 0 and why
it can run fully in parallel with 16-01 and 16-02.
</objective>

<task type="auto">
  <name>Task 2: `davidson_nosym1`</name>
  `crates/pyscf-algebra/src/davidson.rs`. Signature takes `aop` as a closure
  over `&[Complex64] -> Vec<Complex64>` (matrix-free — forming the EOM
  Hamiltonian is exactly what this avoids), `x0` guesses, a `precond` closure,
  and the parameter set above.

  Constraints from this workspace, not from upstream:
  * the projected `heff` is small (`max_space × nroots` square) and **dense
    general complex** — solve it with the same direct `faer` path 17-02
    established (`Eigen::new_from_real` + `num-complex`), not by hand;
  * subspace inner products go through the `oracle_z*` primitives so a run is
    bit-reproducible under `release-oracle` at `RAYON_NUM_THREADS` 1 and 8
    (§9.3). **Name the primitive**: the Gram–Schmidt overlaps are
    `zdotc`-shaped (conjugated), so `oracle_zdot` is correct here — this is the
    one place in the phase where it is, and `16-CONTEXT §3.2` requires the
    site to say so explicitly rather than be assumed;
  * `pyscf-algebra` is a cubecl-owning crate; this solver is **host-only** and
    the module doc says so. It is control flow over small dense algebra, not a
    kernel.
</task>

<task type="auto">
  <name>Task 3: `pick_real_eigs` and the `pick` contract</name>
  `linalg_helper.py`'s `pick_real_eigs` filters the projected spectrum to
  (near-)real eigenvalues and orders them. `eom_kccsd_ghf.py:130-136` supplies
  its own `pickeig` closure and passes it through; `kcis_rhf.py:97-98` uses the
  default. Both paths must work, so `pick` is a first-class parameter with a
  supplied default — not a hard-coded filter.
</task>

<task type="auto">
  <name>Task 4: tests — oracle-free, dense-solver-gated</name>
  `crates/pyscf-algebra/tests/davidson_nosym.rs`:
  1. **Non-symmetric correctness**: for random `n = 40, 80` general complex
     matrices with a well-separated spectrum, the lowest `nroots = 1, 3, 5`
     eigenvalues match the dense `faer` solve to 1e-10, and the residual
     `‖A v − λ v‖` is below `tol_residual` for each returned root.
  2. **Symmetric special case**: on a Hermitian matrix it agrees with
     `eigh_gen` to 1e-11 — the sanity check that a sign or conjugation slip
     would break.
  3. **Matrix-free**: the `aop` closure counts its invocations; assert the
     count is `O(max_space)` per root and that `n²` storage is never
     allocated. This is the property EOM actually needs and the one a
     "compute the matrix then diagonalise" implementation would silently
     violate while passing tests 1 and 2.
  4. **`max_space` trimming** actually triggers: a case needing more than
     `max_space` expansions still converges, proving the collapse path runs.
  5. **`pick`**: a matrix with a deliberately planted complex-conjugate pair
     returns the real roots when `pick_real_eigs` is used.
  6. **Determinism** (§9.3): bit-identical eigenvalues at
     `RAYON_NUM_THREADS` 1 and 8.
  7. **Degenerate/near-degenerate** spectrum and a `lindep` collapse — the two
     paths most likely to silently return `nroots` copies of one vector.
</task>
