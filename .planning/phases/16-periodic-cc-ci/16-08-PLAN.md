<objective>
Port `pyscf/pbc/cc/kccsd_t.py` (319 l, spin-orbital) and `kccsd_t_rhf.py`
(651 l) — `§8.8`'s plan 16-05, sized there at "970 l".

**That sizing omits the file the plan actually depends on.**
`kccsd_t_rhf.py:236` is:

```python
drv = _ccsd.libcc.CCsd_zcontract_t3T
```

a complex C contraction taking 24 raw data pointers (`:229-230`) plus
`mo_offset`/`slices` blocking arrays. This port has no C and no `libcc` — that
is the project's core value proposition, not an accident. So the kernel is
ported to Rust, and the reference it is gated against is
**`kccsd_t_rhf_slow.py` (271 l), which `§8.8`'s table omits entirely**
(`16-CONTEXT §1.7`). It is the loop-explicit form of the same energy and the
only way to check the fast path without a C oracle.
</objective>

<tasks>

<task type="auto">
  <name>Task 1: `kccsd_t_rhf_slow` FIRST</name>
  Port `kccsd_t_rhf_slow.py` before either fast path. It is short, explicit and
  has no blocking, so it is the reference the rest of the plan is measured
  against — and 16-01 Task 4 already measured upstream's own fast-vs-slow
  agreement, so there is a target rather than an argument.

  Porting the fast path first and the reference second is how a blocking bug
  ships: the only thing that would catch it is the final energy gate.
</task>

<task type="auto">
  <name>Task 2: `kccsd_t_rhf` — the blocked path, and the C kernel in Rust</name>
  `kccsd_t_rhf.py:150-300`. Read `CCsd_zcontract_t3T`'s call site
  (`:236-245`) carefully: the 24 pointers, `mo_offset`, `slices`, and what
  `t3Tw`/`t3Tv` are.

  **The blocking is the algorithm, not an optimisation.** `t3` is
  `nocc³ · nvir³` per k-triple and is formed, consumed and discarded per
  `(ka,kb,kc)` block; a port that materialises it over all k trades a
  streaming problem for an allocation that no fixture in `§9.2` can hold
  (`16-REVIEW.md §4.2` gives the byte counts). Port the blocking.

  `LARGE_DENOM` (`:30`) fills the triples denominator for padded orbitals —
  arithmetic, `~1e-28`, not a skip (`16-CONTEXT §3.3`).

  Contractions are host rayon loops with `oracle_*` accumulators
  (D-PBC-29 clause 2), and each site names its primitive.
</task>

<task type="auto">
  <name>Task 3: `kccsd_t` (spin-orbital)</name>
  `kccsd_t.py`, on top of 16-07's `KGCCSD` amplitudes. `tril_product` and
  `cartesian_prod` (`:25`, `:28`) drive the k-loop; port their enumeration
  order exactly — it is observable through the accumulation order and §9.3
  gates bit-identity.
</task>

<task type="auto">
  <name>Task 4: tests</name>
  1. **fast == slow**, same amplitudes, same fixture, bit-identical or to
     1e-13. Same-input/same-formula, so this is the tight one, and it is
     oracle-free. **Written before test 4.**
  2. **spin-orbital == RHF** on a closed-shell system: `kccsd_t`'s correction
     equals `kccsd_t_rhf`'s to 1e-11.
  3. **blocking invariance** — the energy is independent of the block size,
     bit-identically for a fixed accumulation order. This is the test that
     catches a wrong `mo_offset`/`slices` translation.
  4. `e_tot` vs upstream on `test_rccsd_t_shift.py`'s system at 16-01's
     measured tolerance.
  5. Determinism (§9.3) at `RAYON_NUM_THREADS` 1 and 8.
  6. A memory assertion: peak `ZWorkspacePool` live bytes during (T) stay
     below a literal bound proportional to `nocc³·nvir³` for ONE block, not to
     `nkpts³·nocc³·nvir³`. This is what makes Task 2's "the blocking is the
     algorithm" claim testable rather than aspirational.
</task>
