<objective>
The substrate every later Phase-16 plan allocates from and iterates with.
`PBC-MASTER-PLAN §8.8` costs this at **zero** — its Reuse note says
`pyscf-pbc-cc` "MUST reuse" the existing arena, and `16-CONTEXT §1.3` shows
that instruction cannot be followed literally: `WorkspacePool` is f64 all the
way down (`shape_bytes` = `product * 8`, `InMemory(Box<[f64]>)`,
`as_slice -> Vec<f64>`) and every k-point CC tensor is `complex128`.

Three deliverables, none of which needs an SCF to test:

1. a **complex** sibling arena in `pyscf-runtime`, sharing the budget
   accounting / free-list / `InMemory | Spilled` split and the HARD
   `MemoryLimitExceeded` refusal with no silent downgrade;
2. `KptsHelper::build_symm_map` / `transform_symm` / `_operation` in
   `pyscf-pbc-lib` — the ~4× the phase's dominant step depends on
   (`16-CONTEXT §3.1`), which `§8.8` does not mention at all;
3. `KTensor`, the k-indexed complex container the CC blocks and amplitudes are
   expressed in, with the storage tier chosen from a **per-tensor byte count**,
   never from upstream's documented-TODO `_mem_usage` (`16-CONTEXT §3.6`).
</objective>

<tasks>

<task type="auto">
  <name>Task 1: the complex arena — `ZWorkspacePool`</name>
  New `crates/pyscf-runtime/src/zworkspace_pool.rs`, mirroring
  `workspace_pool.rs`'s structure so the two read as siblings:

  * `shape_bytes(shape) = product * 16` — **not** `* 8`. Getting this wrong
    halves every number that reaches the HARD refusal, which is the one place
    an under-estimate is unrecoverable.
  * `TensorBackend` gains a complex variant, or the module carries its own;
    either way the `InMemory | Spilled` split and the HDF5 spill path are the
    same shape as the f64 pool's.
  * `try_reserve` / `reserve(shape, allow_spill)` / `release` / `as_slice` /
    `write_slice` / `with_mut_slice` keep their contracts and their error
    types, over `Complex64` elements.
  * **`WorkspacePool` itself is not edited** beyond whatever `lib.rs`
    re-export is needed. Its f64 API is byte-for-byte unchanged.

  Address `16-REVIEW.md §2.1` and `§2.2` here, in the NEW type, and record in
  the module doc why the f64 pool was not changed to match: it has shipped
  callers and shipped tests, and 16-14 is not the place to discover a
  regression in `pyscf-ccsd`'s `rdm`/`lambda`.
</task>

<task type="auto">
  <name>Task 2: `KptsHelper::build_symm_map` / `transform_symm`</name>
  `crates/pyscf-pbc-lib/src/kpts_helper.rs` already exports `Kconserv`,
  `Kconserv3`, `get_kconserv`, `get_kconserv3` (plan 09-07). Add, porting
  `pyscf/pbc/lib/kpts_helper.py:544-630`:

  * `symm_map: Option<..>` and `_operation: Option<..>`, both `None` until
    built. **`KptsHelper::new` does NOT build them** — `kccsd_rhf.py:512`
    passes `init_symm_map=False` and `_ERIS` builds it lazily at `:783`. A
    `KRCCSD` constructed but never run must not pay `O(nkpts³)`.
  * `build_symm_map(&mut self, kptlist: Option<&[[usize;3]]>)` — the
    `completed` sweep of `:583-612`, assigning each triple exactly one of the
    four operations and appending it to its representative's orbit. **The
    enumeration order is observable** through the orbit lists, so this is an
    ordered map, not a `HashMap` — the same class of defect 17-CONTEXT §3
    recorded for `search_point_group_ops`.
  * `transform_symm(&self, eri, kp, kq, kr)` — `:614-630`, all four ops:
    `identity`, `transpose(2,3,0,1)`, `conj(transpose(1,0,3,2))`,
    `conj(transpose(3,2,1,0))`. **The conjugation on ops 2 and 3 is not
    decoration** (`16-CONTEXT §3.2`); dropping it produces a plausible wrong
    ERI that only the final `e_corr` would catch.
</task>

<task type="auto">
  <name>Task 3: `KTensor` — the k-indexed complex container</name>
  `crates/pyscf-pbc-cc/src/ktensor.rs`. A `(nkpts, nkpts, nkpts)`-indexed block
  tensor over `ZWorkspacePool`, with:

  * a constructor taking the per-block shape and the k-rank, computing the
    **exact** byte requirement as `nkpts^rank * prod(block_shape) * 16` and
    choosing its tier from that — never from `nmo⁴` (`16-CONTEXT §3.6`);
  * three tiers matching `kccsd_rhf.py:423-455`: absent / in-memory / spilled;
  * block accessors that do **not** copy the whole tensor per access
    (`16-REVIEW.md §2.1`) and do not hold a global lock across a contraction
    (`§2.2`) — the two properties the f64 pool lacks and that would otherwise
    serialise every rayon loop in the phase.

  This is `pyscf-pbc-cc`'s own type, not `pyscf-runtime`'s: the k-indexing is
  CC-specific and `pyscf-runtime` sits below `pyscf-pbc-lib`.
</task>

<task type="auto">
  <name>Task 4: tests — all oracle-free, none needs an SCF</name>
  `crates/pyscf-runtime/tests/zworkspace_pool.rs`:
  1. `shape_bytes` — a `[2,3,4]` complex reservation reports **192** bytes, not
     96. Assert the literal number; this is the clause-1 trap.
  2. HARD refusal — a pool with a 1-byte budget refuses an in-core reservation
     with `MemoryLimitExceeded`, and does **not** silently spill when
     `allow_spill == false` (the D-01 contract).
  3. free-list reuse — reserve/release/reserve of a fitting shape does not
     grow `allocation_count` (the bounded-heap guarantee `pyscf-ccsd`'s
     `heap_alloc_count.rs` already pins for the f64 pool).
  4. spill round-trip — `write_slice` then `as_slice` on a spilled complex
     buffer is bit-identical.
  5. the f64 pool is untouched: `cargo test -p pyscf-ccsd` is green.

  `crates/pyscf-pbc-lib/tests/symm_map.rs`:
  6. **completeness** — every one of the `nkpts³` triples appears in exactly
     one orbit, for `nkpts` = 1, 2, 4, 8. Exact integers, no tolerance.
  7. **orbit size ≤ 4** and `sum(len(orbit)) == nkpts³`.
  8. **the group property** — for a random Hermitian-symmetric `eri` block,
     `transform_symm` at each member of an orbit reproduces the directly-built
     block. Since no ERI builder exists yet at wave 0, build the block from a
     synthetic `(pq|rs)` array carrying the 8-fold real-integral symmetries and
     assert the four operations are mutually consistent
     (`op1(op1(x)) == x`, `op2(op2(x)) == x`, `op3 == op1∘op2`).
  9. `build_symm_map` is not called by `KptsHelper::new` — assert `symm_map`
     is `None` after construction.

  `crates/pyscf-pbc-cc/tests/ktensor.rs`:
  10. tier selection — a `KTensor` whose exact size is just under / just over
      the budget lands in-memory / spilled respectively, and the boundary is
      the **exact** byte count, not upstream's `_mem_usage` estimate.
  11. block accessor round-trip is bit-identical, in-memory and spilled.
  12. two rayon threads writing two different blocks concurrently make
      progress (`16-REVIEW.md §2.2`) — a smoke test that the container does
      not serialise on one lock.
</task>
