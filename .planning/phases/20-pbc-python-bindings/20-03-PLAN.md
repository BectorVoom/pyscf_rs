<tasks>

<task type="auto">
  <name>Task 1: add the `pbc-oracle` job</name>
  Model it on the existing job bodies. Steps, in order:

  1. `actions/checkout@v4`
  2. `./.github/actions/setup-sibling-crates` — **without** `SETUP_LIBXC_RS`
  3. `dtolnay/rust-toolchain@stable`, `Swatinem/rust-cache@v2` with its own key
  4. build the venv and `pip install "pyscf==2.12.1" "numpy>=1.26" "scipy>=1.11" "h5py>=3.10"`
  5. the version assertion (Task 2)
  6. the T1 run (Task 3)

  Trigger on `push` and `pull_request`.
</task>

<task type="auto">
  <name>Task 2: assert the oracle version in the job</name>
  Belt and braces — 47 Rust test files already assert `2.12.1` internally, and
  the job must not be weaker:

  ```bash
  V=$(.venv/bin/python -c "import pyscf; print(pyscf.__version__)")
  [ "$V" = "2.12.1" ] || { echo "oracle is $V, expected 2.12.1"; exit 1; }
  ```
</task>

<task type="auto">
  <name>Task 3: run the T1 set with named targets</name>
  For each crate in 20-02's T1 list, one step naming its test targets:

  ```bash
  export CARGO_TARGET_DIR=$HOME/.cargo-target-gate    # never /tmp
  PYSCF_ORACLE_VENV=1 cargo test -p <crate> --release --locked \
      --test <target1> --test <target2> -- --ignored
  ```

  Never `--tests` bare. Never `ulimit -v`. Keep `--test-threads` at the default
  unless 20-02 recorded a memory ceiling for that crate.
</task>

<task type="auto">
  <name>Task 4: add the T2 nightly and T3 manual jobs</name>
  `pbc-oracle-nightly` on `schedule` (T1 + T2) and `pbc-oracle-full` on
  `workflow_dispatch` (all tiers). Same venv and version assertion; reuse via
  YAML anchors or a composite action rather than three copies.
</task>

<task type="auto">
  <name>Task 5: prove the job can fail</name>
  Temporarily tighten one T1 gate's tolerance by an order of magnitude, confirm
  the job goes red, then revert. A CI job never observed to fail is not known
  to work. Record both runs in the plan SUMMARY.
</task>
