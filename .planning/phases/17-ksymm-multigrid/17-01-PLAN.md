<objective>
**Measure the gate before writing it.** `ROADMAP.md` says Phase 17's gate is
"symmetry-restricted energies equal full-BZ energies to **1e-14**".
`PBC-MASTER-PLAN.md:446` says **1e-9**. Upstream's own test suite asserts
**5e-8** (gamma-centred) and **5e-7** (Monkhorst) for exactly that comparison
(`scf/test/test_khf_ksym.py:84, 92`).

So `1e-14` is six to seven orders tighter than what the reference implementation
demands of itself, and would fail a byte-perfect port. This is the third phase
running where the recorded gate was an unmeasured guess
(`14-CONTEXT §2`, `15-CONTEXT §2.1`); Phase 14 only escaped a rewrite because
the correction landed *before* the code.

**This plan writes no Rust.** It runs upstream against itself, records what the
achievable floors actually are, and rewrites `17-CONTEXT.md §2`,
`ROADMAP.md`'s Phase-17 line and `PBC-MASTER-PLAN.md §7`/`§8.9` **together** so
the three documents cannot drift again.
</objective>

<task type="auto">
  <name>Task 2: the transform floor, against ONE converged SCF (Gate B)</name>
  Upstream's `test_kpts_ksymm.py:90-143` asserts 7–8 decimals — but against a
  **`max_cycle=1`** reference (`:46-48`). That is not a floor, it is a default.

  Re-run it with `conv_tol = 1e-11` and a converged `KRKS`, on `si` at `[3,3,3]`,
  and record `abs(...).max()` for each of:
  `transform_dm`, `transform_mo_occ`, `transform_mo_energy`,
  `transform_1e_operator` (fock), `symmetrize_density`, and
  `make_rdm1(transform_mo_coeff(...))`.

  **Do NOT compare `mo_coeff` elementwise** — 17-CONTEXT §3.1: it is defined only
  up to a unitary within each degenerate subspace, and upstream's own test
  compares the DM built from the transformed MOs, never the coefficients.
  Additionally record, for evidence: `abs(mo_coeff_bz - transform_mo_coeff(...)).max()`
  **as a demonstration that it is large**, so the trap is proven rather than
  asserted.

  Expectation from 17-CONTEXT §2.2: these are exact linear maps and should land
  at **≥1e-12**. If any lands at 1e-7, find out which one and why *before* the
  gate is written — that would mean the map is not exact and the whole Gate-B
  framing is wrong.
</task>

</task>

<task type="auto">
  <name>Task 5: the multigrid floor (Gate E)</name>
  Multigrid is a **different quadrature**, not a different implementation of the
  same one, and upstream's own tests say so: `dft/test/test_multigrid.py:84-129`
  gates `get_pp`/`get_nuc`/`get_j` at 8 decimals and `:139-217` gates the XC
  potential, `exc` and `ecoul` at 7.

  Measure, for `MultiGridNumInt` (v1) and `MultiGridNumInt2` (v2) separately,
  against the reference `pbc.dft.numint`:

  * `get_nuc`, `get_pp`, `get_j` — max-abs residual
  * `vxc`, `exc`, `ecoul` for LDA and a GGA
  * converged `KRKS` `e_tot`
  * on `diamond` and `si`, and at **two meshes**, so the phase learns whether
    the residual is a convergence artefact (shrinks with mesh) or a definitional
    one (does not). That distinction decides whether Gate E can be stated
    monotonically — Phase 14's MDF ladder is the precedent for a gate that
    would have failed a correct implementation had it assumed monotonicity.

  Also record the **v1 vs v2** difference on the same quantities. They are two
  implementations of the same idea and their disagreement is a floor no port can
  beat, exactly as upstream's two GDF builders' 4.5e-6 was for Phase 14.
</task>
