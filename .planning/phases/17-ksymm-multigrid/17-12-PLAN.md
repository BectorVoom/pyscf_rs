<task type="tdd">
  <name>Task 2: grid_collocate_drv / grid_integrate_drv</name>
  The two workhorses. `collocate` puts density-matrix-weighted Gaussian products
  on the grid; `integrate` contracts a grid function back into the AO basis.
  They are transposes of one another.

  **That transposition is the strongest oracle-free test in this plan:**

  ```
  <integrate(f), D>  ==  <f, collocate(D)>     to 1e-13
  ```

  for random `f` and `D`. It catches a wrong grid offset, a wrong image wrap and
  a wrong normalisation in either kernel — and it needs no upstream. Write it
  first.

  Then the per-`l` tests of 17-11 Task 2, extended to the pair form and to the
  GGA derivative components.
</task>

<task type="tdd">
  <name>Task 3: the G-space helpers</name>
  `_backend_c.py`'s `gradient_gs` and `get_gga_vrho_gs`, and
  `multigrid/utils.py` (70 l).

  `gradient_gs` is documented in its own source as "equivalent to
  `einsum('np,px->nxp', f_gs, 1j*Gv)` with multithreading" — so it has an exact,
  trivially correct reference, and the test is that equivalence at 1e-14. Take
  the free oracle.

  `get_gga_vrho_gs` combines the GGA potential's density and gradient parts in
  G-space; test it against the real-space route already in
  `crates/pyscf-pbc-dft/src/numint.rs` on a fine mesh, where the two must agree
  to the mesh's own truncation.

  Existing FFT (`pyscf-pbc-tools/src/fft.rs:96, 110`) is reused; no new
  transform.
</task>

<task type="tdd">
  <name>Task 4: pp.py — the pseudopotential on the multigrid</name>
  `multigrid/pp.py` (256 l) plus `_backend_c.py`'s `int_gauss_charge_v_rs` and
  `build_core_density`.

  This is `get_pp` computed through the multigrid rather than through AFTDF.
  Phase 14 recorded a hard-won fact that binds here: **upstream's `aft.get_pp`
  and `pp_int.get_pp_loc_part2` disagree with each other by 1.7933e-9** in
  2.12.1 (13-VERIFICATION Gate 3). So a multigrid `get_pp` is being compared
  against a quantity that upstream itself computes two ways.

  Gate it against **the route this port already ships and oracle-gated at
  2.755e-12** (AFTDF `get_nuc`), name that route in the test, and record the
  residual against upstream's multigrid `get_pp` separately rather than folding
  the two comparisons into one number.

  `pp.py` imports `KPoints` — after 17-05 Task 6 the type is nameable from
  `pyscf-pbc-dft`, so the IBZ path works here for free.
</task>

<task type="tdd">
  <name>Task 5: MultiGridNumInt2, and the v1-vs-v2 floor</name>
  Assemble the v2 numint and gate it per Gate E, at 17-01 Task 5's numbers,
  against `test_multigrid2.py`.

  **Also gate the v1-vs-v2 difference.** They are two implementations of the same
  idea and their disagreement is a floor no port can beat — exactly the role
  upstream's two GDF builders' 4.502e-06 played for Phase 14, where reproducing
  the *inter-route gap* to within 1 % became "the strongest single piece of
  evidence in the phase". 17-01 Task 5 measured upstream's v1-vs-v2 gap; assert
  the port reproduces it, and report the ratio the way 14-VERIFICATION Gate 3
  does.

  **The speed half (17-CONTEXT §8 corollary):** time `MultiGridNumInt2`'s

  17-11's measurement, and report the ratio next to 17-01 Task 6's v2 number in
  the same table as Gate E — not as separate prose. Also report v2's ratio
  against v1's own wall time; a v2 that is more accurate but slower than v1 is
  a real trade-off Phase 18 needs to know about, since it is v2 that
  `grad/rhf.py`/`grad/uhf.py` require regardless of which is faster.

  Finally, record for Phase 18 that `MultiGridNumInt2` is the class
  `grad/rhf.py:44` and `grad/uhf.py:40` assert on, so the gradient plans know
