<objective>
`khf_ksymm.py` (410 l), `kuhf_ksymm.py` (219 l), `kghf_ksymm.py` (211 l) — the
IBZ-restricted SCF.

**D-PBC-15 is satisfiable literally here, and that is the plan's main
architectural claim.** `crates/pyscf-pbc-scf/src/kscf.rs` is a single
`kernel<H: KOverrideHooks>` loop and `khooks.rs:21` is an eleven-method trait
that already carries `cell()`, `kpts()`, `get_ovlp`, `get_hcore`,
`get_init_guess`, `get_veff`, `eig`, `get_occ`, `make_rdm1`, `energy_elec`,
`get_grad`. The ksymm layer is **another implementation of that trait** whose
`kpts()` returns the IBZ points — not a second driver, not a fork, not a copy.
If this plan finds itself editing `kscf.rs`, something is wrong with the design
and it should stop and say so.
</objective>

<task type="auto">
  <name>Task 0: the k-set indirection, decided once</name>
  `KOverrideHooks::kpts()` returns `&[[f64; 3]]`. The ksymm impl returns
  `kpts.kpts_ibz`. Everything downstream — `nkpts`, the `idx(set, k)` layout in
  `KScfResult`, DIIS's `KFockSubspace` — then works on IBZ indices with no
  change.

  Two consequences to settle **before** writing any method, because reversing
  either is a rewrite:

  1. **`KScfResult` carries IBZ-length arrays.** Any consumer wanting BZ arrays
     unfolds explicitly through `KPoints`. Do *not* silently unfold at the end
     of the driver — upstream does not (`khf_ksymm.py` keeps IBZ arrays and its
     `to_khf()` at `:336` is the explicit converter), and a silent unfold makes
     `mo_coeff`'s meaning depend on which class produced it.
  2. **`get_veff` needs BZ densities — for the reference route.** `get_jk`
     (`khf_ksymm.py:250-277`) transforms the IBZ density to the full BZ, calls
     the ordinary `PeriodicDf::get_jk` over all `nkpts`, then folds the result
     back to the IBZ. **The DF layer stays untouched** — it never learns about
     symmetry. This is the crux of D-PBC-15 and it is why 17-05 Task 6 only made
     `KPoints` *nameable* from `pyscf-pbc-df` rather than changing it.

     **This literal route ships and is the default and the Gate C/D
     reference.** Task 7 adds a second, faster route (D-PBC-26,
     17-CONTEXT §8) that calls `PeriodicDf::get_jk` only at `kpts_ibz` and
     unfolds the result via `transform_1e_operator` instead — still without
     the DF layer learning anything, since it only ever sees a plain k-point
     list, now sometimes shorter. Both routes stay in the tree; the fast one is
     validated against the reference one, not against upstream.
</task>

<task type="tdd">
  <name>Task 1: get_occ — one Fermi level over the UNFOLDED BZ</name>
  `khf_ksymm.py:31-67`. **17-CONTEXT §3.4.** The function transforms
  `mo_energy` to the full BZ (`:39`), sorts *that* (`:40`), takes
  `fermi = mo_energy[nocc - 1]` with `nocc = cell.tot_electrons(kpts.nkpts)//2`
  (`:38`), assigns occupations, and folds back through `check_mo_occ_symmetry`
  (`:65`).

  Fusing the unfold into the IBZ loop gives a different occupation on any cell
  with a k-dependent gap — risk R-06, which the project already has a named test
  for ("for a metal at 2×2×2, occupancies differ between k-points", plan 11-09).
  Extend that test to the ksymm path rather than writing a new one.

  `check_mo_occ_symmetry` (`kpts.py:717`) **raises** when the occupations are not
  symmetric — that is a real physical condition (a symmetry-broken state), not an
  internal error. Surface it as a typed error naming the k-point and the
  tolerance, not a panic.
</task>

<task type="tdd">
  <name>Task 2: energy_elec and get_init_guess — name every weight</name>
  `khf_ksymm.py:69-86` and `:387-408`. **17-CONTEXT §3.5.**

  ```
  energy_elec:     e_coul = einsum('k,kij,kji', kpts.weights_ibz, dm, vhf) * 0.5
  get_init_guess:  ne = einsum('k,kij,kji', kpts.weights_ibz, dm, s1e).real
                   ne *= nkpts                       # :398 — the BZ count
  ```

  `15-CONTEXT §3` recorded the analogous KMP2 trap ("`1/nkpts` appears at three
  sites and is two distinct divisions"). Do the same here: **enumerate every
  weighted sum in all three adapters in a module-level doc comment, and state
  for each whether it takes `weights_ibz`, `1/nkpts`, or a bare sum.** A reader
  should not have to diff against upstream to answer that question.

  `get_init_guess` also handles three input shapes (`:390-394`): a 2-d Γ density
  broadcast, an already-IBZ-length stack, and a full-BZ stack to be sliced by
  `ibz2bz`. All three occur in practice (chkfile restart hits the third). Test
  all three.
</task>

<task type="tdd">
  <name>Task 3: eig — the symmetry-adapted and time-reversal branches</name>
  `khf_ksymm.py:104-141` and `:291-298`. Three routes:

  * **`use_ao_symmetry = true`** (the DEFAULT, `:142` `ksymm_scf_common_init`) —
    block-diagonalise `F` in `cell.symm_orb` by `cell.irrep_id` and solve each
    irrep block separately. Needs 17-04. 17-04 Task 4's block-diagonality test
    is the precondition; if that test is green this branch is mechanical.
  * **`eig_trs`** (`:121-141`) — at time-reversal-invariant momenta the
    Hamiltonian can be made real, and upstream exploits it. `trs_mask =
    is_trim(cell, kpts.kpts_ibz)` (`:126`), from 17-05 Task 2. Upstream tests
    that the resulting `mo_coeff` is **real** at those k-points
    (`test_khf_ksym.py:341-348`, `abs(mo_coeff[k].imag).max() == 0` to 8
    decimals) — port that test, it is oracle-free and it is the only thing that
    proves the branch was taken.
  * **plain** (`use_ao_symmetry = false`) — delegate to the existing
    `KRHF::eig`.

  All three must ship, because 17-07 is the first plan where an
  `use_ao_symmetry = false` fallback is even meaningful, and having it makes any
  17-04 defect immediately bisectable.

  §9.3 applies: complex eigenvector phases canonicalised via
  `canonicalize_signs` on the real part, exactly as the non-symmetric path does.
</task>

<task type="tdd">
  <name>Task 4: get_rho, get_ovlp, get_hcore, dump_chk, to_khf</name>
  `khf_ksymm.py:87-103` (`get_rho` — transforms the DM to the BZ first, `:101`),
  `:236-249` (`get_ovlp`/`get_hcore` at the IBZ points), `:278-290`
  (`init_guess_by_chkfile`, `dump_chk`), `:299-318` (`get_orbsym`), `:336-376`
  (`to_khf`).

  `to_khf` is the explicit IBZ→BZ converter and the counterpart to Task 0's
  ruling that nothing unfolds silently. Upstream gates it at 8 decimals
  (`test_khf_ksym.py:288-316`) across five method classes.

  The chkfile path matters more than it looks: upstream's `kpts` property
  (`khf_ksymm.py:171-177`) **raises** when a chkfile's k-point count disagrees
  with the current `KPoints.nkpts_ibz`, because a restart that silently
  reinterprets IBZ indices as BZ indices produces a plausible wrong answer. Port
  the check. Upstream gates restart at 9 decimals (`:164-194`).
</task>

<task type="tdd">
  <name>Task 5: KUHF and KGHF</name>
  `kuhf_ksymm.py` (219 l), `kghf_ksymm.py` (211 l). Two spin channels and the
  `2·nao` GHF block respectively, over the same `KOverrideHooks` surface —
  `nset()` and `nao()` already carry both distinctions (`khooks.rs:29-42`).

  KUHF's `get_occ` has two Fermi levels, one per channel, each computed over the
  unfolded BZ. Everything from Tasks 1–4 applies per channel.

  KROHF has **no** upstream `*_ksymm` module. Do not invent one; if a caller asks
  for one, refuse with the upstream absence in the message, exactly as
  15-CONTEXT ruled for `KUMP2`'s missing kernel.
</task>

<task type="tdd">
  <name>Task 6: the get_jk fast path (D-PBC-26, 17-CONTEXT §8)</name>
  Add the second `get_jk` route ruled on in 17-CONTEXT §8: call
  `PeriodicDf::get_jk` only at `kpts.kpts_ibz` (the IBZ-length density slice,
  already available before Task 0's full-BZ unfold), then unfold `vj`/`vk` to
  the full BZ with `transform_1e_operator` (17-03 Task 6 / 17-05 Task 3) instead
  of calling the DF builder over all `nkpts`. Fold the unfolded result back to
  the IBZ exactly as the reference route does, so both routes present the same
  `KOverrideHooks::get_veff` contract.

  **Validation, per D-PBC-26 point 2: against this plan's own reference route,
  never against upstream.** On every §9.2 cell, both k-mesh types, `GDF` and
  `FFTDF`: `|vj_fast(k) - vj_reference(k)|` and the same for `vk`, at every BZ
  k-point, to **1e-13**. This is the same idiom as 17-10 Task 4's MO-factorised
  `get_k_kpts` — two routes to the same number inside one process.

  Ship the fast path **behind a flag, reference route as the default**, until
  the 1e-13 equivalence holds on every fixture; then Task 7 measures and gates
  the speedup. If the equivalence does not hold within 1e-13 on some fixture,
  that is evidence the assumed equivariance breaks somewhere concrete (a
  non-symmorphic op, a TRIM point, a `use_ao_symmetry` interaction) — report
  which fixture and why, do not loosen the tolerance to make it pass.

  Following D-PBC-26 point 6: if the fast path measures **slower** than the
  reference route on the CPU backend once Task 7 times it, record that finding
  and leave the reference route as the only shipped one — `zgemm_dense` is the
  standing precedent for a "faster" route that lost.
</task>
