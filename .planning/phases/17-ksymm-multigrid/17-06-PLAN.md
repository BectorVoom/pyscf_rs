<objective>
`pyscf/pbc/lib/ktensor.py` (386 l) — the `KsymmArray` container that stores only
the IBZ-irreducible blocks of a k-indexed tensor and materialises the rest on
demand through the rotation matrices.

**This plan is here because `15-CONTEXT.md §1.1` put it here.** `§8.7` had
scheduled `ktensor` in Phase 15; the pre-implementation read found that its
`transform_2d`/`transform_4d` take `rmat` rotation matrices and that its only
consumers are `kmp2_ksymm.py`, `khf_ksymm.py` and `kccsd_rhf_ksymm.py` — so
building it in Phase 15 would have produced "a container with no caller and no
way to test it". `PBC-MASTER-PLAN §8.9` was never updated to receive it
(17-CONTEXT §1.3); 17-01 Task 7 fixes the table.

The same reasoning binds this plan: **`KsymmArray` is only worth shipping
alongside a caller.** It is sequenced immediately before 17-07 for that reason,
and its acceptance test is a real `khf_ksymm` Fock store, not a synthetic one.
</objective>

<task type="tdd">
  <name>Task 1: the container</name>
  `ktensor.py:26-227`. `empty`/`empty_like` (`:26-41`), `class KsymmArray`
  (`:42`) with `_init` (`:54`), the shape/dtype/order accessors (`:84-108`),
  `__getitem__`/`__setitem__` (`:109-124`) dispatching to `_getitem_2d`
  (`:125`), `_getitem_4d` (`:140`), `_setitem_2d` (`:158`), `_setitem_4d`
  (`:170`), plus `todense` (`:180`), `fromdense` (`:185`), `fromraw` (`:209`),
  `zeros` (`:223`) and `_guess_input_order` (`:228`).

  Rust shape:
  * The subarray order (`subarray_order`, C or F) is part of the type, not a
    runtime string — but it must still round-trip through `fromraw`, which
    upstream uses to wrap a buffer it did not allocate. Model it as an enum
    stored on the struct.
  * `metadata` carries the `KPoints` reference and the k-index map. Hold it as a
    borrow or an `Arc`, never a clone of the `KPoints` — the same argument
    17-CONTEXT §3.9 makes for `Symmetry` not owning a `Cell`.
  * `incore` vs out-of-core (`_init`, `:54-83`): upstream falls back to an HDF5
    dataset when the tensor does not fit. **This is the point of the class** —
    a k-symmetry CCSD `Wvvvv` is `nkpts³ × nvir⁴`. Route the out-of-core path
    through `pyscf_chkfile::hdf5` like every other crate (D-07), not through a
    direct `hdf5-metno` dependency; `pyscf-pbc-df` already had that dependency
    removed for exactly this reason (plan 14-03 Task 0).

  Tests: `fromdense`/`todense` round-trips bit-exactly for 2-d and 4-d; a
  `__setitem__` at a non-irreducible key writes to the irreducible representative
  and reads back transformed; out-of-core and incore give identical results on a
  tensor small enough to hold both ways.

  **Speed:** measure, do not guess, where the incore/out-of-core crossover
  should sit. Time `fromdense`/`todense` and a representative `transform_4d`
  unfold at a few tensor sizes spanning the boundary upstream picks
  (`ktensor.py:54-83`'s own heuristic), and record the wall-clock cost of
  forcing out-of-core below that size — a threshold set from upstream's
  Python-level constant without checking the Rust HDF5 path's own overhead is
  exactly the kind of unmeasured number 17-01 exists to prevent elsewhere in
  this phase.
</task>

<task type="tdd">
  <name>Task 2: set_2d / set_4d and the index algebra</name>
  `ktensor.py:240-265` (`set_2d`, `set_4d`), `:339-368` (`index_to_coords`,
  `slice_to_coords`).

  `set_4d` takes `(kpts, kqrts, klc)` — the k-quartet table and the
  little-cogroup labels — and decides which of the `nkpts³` blocks is stored.
  Getting this map wrong stores the right numbers at the wrong key, which the
  round-trip test in Task 1 would *not* catch if the same wrong map is used for
  reading. **So the test here is against an independently computed dense
  tensor**, exactly as 15-CONTEXT insisted for the `ao2mo_7d` index contract.

  `index_to_coords`/`slice_to_coords` are pure index arithmetic; test them
  exhaustively at small `nkpts`, not by sampling.
</task>

<task type="tdd">
  <name>Task 3: transform_2d / transform_4d</name>
  `ktensor.py:266-338`. Materialise a non-stored block by applying the rotation
  matrices `rmat` with a `label` (which quantity: dm, fock, mo_coeff) and a
  `trans` flag (whether the op is time-reversal, i.e. whether to conjugate).

  **The `trans` flag is the trap.** Time-reversal acts antiunitarily: the
  transformed block is conjugated. `14-VERIFICATION` recorded the same class of
  defect twice — `gen_uniq_kpts_groups`'s missing `if self_conj: j2c = j2c.real`
  and its missing `_conj_j2c` pass, both invisible on the route that happened to
  be tested. Enumerate the `(label, trans)` combinations and test each; do not
  test one and assume the rest.

  Invariants that need no oracle:
  * `transform_2d(block, identity_op) == block` exactly.
  * unfolding the whole IBZ through `transform_2d` and refolding reproduces the
    stored blocks bit-exactly.
  * for a Hermitian input the output is Hermitian, for every op and both `trans`
    values.

  **Speed:** unfolding a whole `KsymmArray` (e.g. every block 17-09's MP2/CCSD
  loops need) is an independent `transform_2d`/`transform_4d` call per
  non-stored key, writing to a disjoint slot. Parallelise that unfold loop with
  rayon; it needs the same disjoint-write argument as 17-05's star unfolds, not
  `oracle_sum`, because each output block has exactly one writer. Gate it with
  `RAYON_NUM_THREADS` 1-vs-8 bit-identity, same as everywhere else in the phase.
</task>

<task type="tdd">
  <name>Task 4: the acceptance test uses a real caller</name>
  Not synthetic. Take the converged full-BZ `KRKS` fixture 17-05 already builds,
  store its Fock matrices as a `KsymmArray` over the IBZ, read back every BZ
  k-point, and compare to the dense full-BZ array at 17-01 Task 2's Gate-B
  floor.

  This is the assertion that makes the plan safe to land before 17-07: it proves
  the container against a quantity that exists today, so a later failure in
  `khf_ksymm` cannot be blamed on the storage layer.
</task>
