<task type="tdd">
  <name>Task 1: numint takes an IBZ k-set</name>
  The seven `isinstance(kpts, KPoints)` sites in `pbc/dft/numint.py` all do the
  same thing: when the k-set is symmetric, evaluate AOs and the density at the
  IBZ points, then **symmetrize the real-space density** through
  `kpts.symmetrize_density` (17-05 Task 4) instead of averaging over the full BZ.

  In Rust this is an enum parameter, not a downcast:

  ```rust
  pub enum KSet<'a> { Full(&'a [[f64; 3]]), Ibz(&'a KPoints) }
  ```

  threaded through `numint.rs`'s density and potential builders. **One enum, one
  match per builder** — not a `KPoints` field bolted onto each function, which
  would let the two paths drift.

  Two properties to hold onto:
  * `KSet::Full` must produce **bit-identical** results to today's code. Assert
    it: the existing `numint` tests run unchanged against the new signature and
    must not move by one ulp. That is the whole safety argument for touching a
    file the whole DFT stack sits on, and W-06 already parallelised its grid
    contractions over disjoint rows, so the summation order is well-defined
    enough to make bit-identity a fair demand.
  * The symmetrized path is a D-PBC-17 accumulation and inherits 17-05 Task 4's
    `oracle_sum` treatment and its `RAYON_NUM_THREADS` bit-identity gate.
</task>

<task type="tdd">
  <name>Task 2: krks_ksymm.get_veff and energy_elec</name>
  `krks_ksymm.py:29-87`, `:118-138`.

  `get_veff` computes the XC potential on the symmetrized density at the IBZ
  points, then adds `vj`/`vk` obtained the 17-07 Task 0 way — transform the DM
  to the BZ, call the untouched `PeriodicDf::get_jk`, fold back.

  **If 17-07 Task 6 shipped the D-PBC-26 fast `get_jk` route, use it here
  too**, behind the same flag. The XC half is already IBZ-native through
  `numint`'s `KSet::Ibz` arm (Task 1); once the `vj`/`vk` half also runs at
  `nkpts_ibz` instead of `nkpts`, `KRKS`/`KUKS`'s `get_veff` is fully
  IBZ-costed end to end. There is nothing new to validate here beyond what
  17-07 Task 6 already proved — reuse its equivalence test's conclusion, do not
  re-run a second 1e-13 comparison against a DFT-specific reference.

  `energy_elec` (`:118-138`) is a **`weights_ibz`** sum (17-CONTEXT §3.5), and
  it carries the `exc`/`ecoul` bookkeeping that `krks.rs` already has for the
  non-symmetric path. As in 17-07 Task 2, enumerate every weighted sum in a
  module doc comment.

  The hybrid/RSH branch matters: `test_krks_ksym.py:143-157` covers `rsh` and
  `:197-214` covers `rsh` on GDF. RSH reaches `get_jk(omega=…)`, which
  `crates/pyscf-pbc-df/src/gdf/jk.rs:259` currently refuses with
  `NotYetImplemented { phase: 14 }` — **check whether plan 14-07's
  `range_coulomb` work closed that**, and if not, this plan ships the LDA/GGA
  gates and records RSH as blocked on the Phase-14 carry-over rather than
  working around it.
</task>

<task type="tdd">
  <name>Task 4: krkspu_ksymm / kukspu_ksymm — the DFT+U projectors</name>
  `krkspu_ksymm.py` (72 l), `kukspu_ksymm.py` (59 l), over
  `crates/pyscf-pbc-dft/src/kspu.rs` (716 l, shipped in Phase 12).

  These are short because the only thing that changes is that the **local
  projectors `C_ao_lo` must be rotated with the space group** when the density
  is unfolded — a Hubbard `U` on a d shell is defined in a local frame, and an
  IBZ run that forgets to rotate it applies `U` to the wrong orbital at every
  symmetry-related site. That is a large, plausible-looking energy error.

  Upstream's own tests are `dft/test/test_krkspu.py:77` and
  `test_kukspu.py:77`, both of which construct the cell with
  `space_group_symmetry=True, time_reversal_symmetry=True`. Gate against them,
  and add the oracle-free check that the occupation matrix `n_{IJ}` is invariant
  under every op of the little co-group at each site.
</task>
