<objective>
The three nuclear-gradient contributions that come from the one-electron and
nuclear side: `vpploc_part2_nuc_grad`, `vppnl_nuc_grad` and `ewald_nuc_grad`.

`PBC-MASTER-PLAN §2.4` marks the five cintx families this needs as
**"declared, unverified, no dispatch arm — BLOCKS plan 18-01"**, and `§8.10`
plans an `#[ignore]` fallback around them. **Both are stale.** All five are in
the manifest at *byte-for-byte the same status* as the five families this port
already runs GTH pseudopotentials on, the port already carries the feature that
enables them, and the port already has the test that proves cintx refuses
rather than falling open to the unweighted parent (`18-CONTEXT §1.3`). This
plan enables them and extends that test; it does not defer anything.

`§8.10`'s other half of 18-01 — `int1e_ipovlp`/`int1e_ipkin` over lattice
images — is **already shipped** (`pbc_intor.rs:275-277`, tested at
`tests/pbc_intor.rs:375`), so it is verified here rather than written.
</objective>

  `int3c1e_ip1_r{2,4,6}_origk_sph` and `int1e_r{2,4}_origi_ip2_sph` are
  `profiles="unstable-source"`, `oracle_covered=false`,
  `stability="unstable_source"` — identical to `int3c1e_r{2,4,6}_origk_sph` and
  `int1e_r{2,4}_origi_sph`, which `gth-pp` already turns on and which every
  reference cell's `hcore` already depends on.

  Extend `tests/cintx_moment_weighted_available.rs` to the five derivative
  symbols, asserting both halves of what `Cargo.toml:60-63` records for the
  energy half: **with** the feature they evaluate, and **without** it
  `SessionRequest::evaluate` returns the named
  `"source-only symbol … requires feature \`unstable-source-api\`"` error —
  **not** the unweighted parent. That is R-14 for this family class, and this
  test is the mechanism that keeps it disproved.

  records. Say so in the module doc.
