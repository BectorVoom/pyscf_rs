<objective>
`pyscf/pbc/geomopt/geometric_solver.py` (246 l) and `__init__.py` (23 l) — the
periodic geometry optimizer.

**`§8.10`'s 18-06 asks for lattice degrees of freedom. Upstream has none.**
`grep -rn "lattice" pyscf/pbc/geomopt/*.py` returns exactly one hit,
`geometric_solver.py:223`, inside the `__main__` example block. The optimizer
moves atoms and nothing else (`:80-81`, `cell.set_geom_(coords, unit='Bohr')`
then `g_scanner(cell)`); there is no `cell.a` update and no strain coordinate
anywhere in `pyscf/pbc`. Variable-cell relaxation is invented scope with no
upstream oracle, and D-PBC-15 ("add-on layer, never a fork") forbids shipping
it inside the port surface (`18-CONTEXT §1.7`).

This plan ports what exists.
</objective>

<tasks>

<task type="auto">
  <name>Task 1: the engine seam — reuse, do not rewrite</name>
  `crates/pyscf-geomopt` already ships the native optimizer: `rfo.rs` (434 l),
  `internals.rs` (267 l), `bmatrix.rs` (350 l), `backtransform.rs` (176 l),
  `converge.rs` (147 l), `checkpoint.rs` (235 l), with `GeometryOptimizer`
  (`lib.rs:100`) and `optimize` (`:187`) on top.

  What is periodic-specific is the **engine adapter**, i.e. upstream's
  `PySCFEngine.calc_new` (`:65-90`): displace, run the scanner, return
  `{energy, gradient}`. Everything above it — internal coordinates, the RFO
  step, convergence testing, checkpointing — is coordinate-space work that does
  not know the system is periodic.

  Write the adapter. **Do not add a second optimizer**; `pyscf-geomopt`'s
  engine is the one this project already gates.
</task>

<task type="auto">
  <name>Task 2: `kernel` and `optimize`</name>
  Port `:91-176`. Details that matter:

  * `:113-122` accepts three input shapes — an existing `GradScanner`, a
    `GradientsBase`, or a method with `nuc_grad_method` — and raises
    `NotImplementedError('Nuclear gradients of %s not available')` otherwise.
    That last branch is the one a GDF-backed `KRHF` hits (18-04 Task 4);
    make sure the error that surfaces names the DF route, not just the method.
  * `:123-124` — `include_ghost=False` restricts `atmlst` to atoms with nonzero
    charge. Ghost atoms are in the basis but not the optimization.
  * `:131` — `engine.cell = g_scanner.cell.copy()`, *"to avoid overwriting
    method.mol"*. The optimizer must not mutate the caller's cell; the copy is
    load-bearing and a test asserts the input cell is unchanged after
    `optimize` returns.
  * `:145-152` — `kernel` returns `(conv, cell)` and `optimize` returns
    `kernel(...)[1]`. Two different return shapes on two public entry points.
  * `:132-137`'s comment about symmetry shifting/rotating the molecule between
    steps applies here too, and `17-CONTEXT` recorded the periodic version of
    that hazard (`check_mesh_symmetry` can enlarge `cell.mesh`). Pin the mesh
    across optimization cycles, or the energy being minimised changes underneath
    the optimizer.

  Convergence defaults are upstream's documented set (`:161-167`):
  `energy 1e-6 Eh`, `grms 3e-4 Eh/Bohr`, `gmax 4.5e-4 Eh/Bohr`,
  `drms 1.2e-3 Å`, `dmax 1.8e-3 Å`. `pyscf-geomopt`'s `converge.rs` already
  holds the molecular equivalents; confirm they match rather than duplicating
  the constants.
</task>

<task type="auto">
  <name>Task 3: both entry points, including the one that refuses</name>
  Upstream exposes the optimizer twice, and only one of them works:

  * `pyscf.pbc.geomopt.optimize(method, ...)` (`__init__.py:18-23`) → the
    geomeTRIC solver. **This is the working path.**
  * `mf.nuc_grad_method().optimizer(solver='ase')`
    (`pbc/grad/krhf.py:290-298`, `pbc/grad/rhf.py:169-178`) → accepts **only**
    `'ase'`; any other value, including `'geometric'`, raises
    `RuntimeError(f'Optimization solver {solver} not supported')`.

  So the `optimizer()` method **cannot reach the module this plan ports**.
  Mirror both, including the refusal — 18-02 Task 1 already declared it and
  18-05 Task 5 wired it. A drop-in port that "helpfully" makes
  `optimizer('geometric')` work diverges from upstream on the default surface.

  The `'ase'` branch itself belongs to Phase 20's `tools/pyscf_ase`
  (`§8.12`, 20-02); here it is a `NotYetImplemented { phase: 20 }` seam, which
  is a *different* error from the `RuntimeError` an unrecognised solver gets.
  Both are tested.
</task>

<task type="auto">
  <name>Task 4: restate the ROADMAP</name>
  `ROADMAP.md:464` says *"periodic geometry/lattice optimization"*. Strike the
  lattice half and record why in one sentence, citing
  `grep -rn "lattice" pyscf/pbc/geomopt/*.py`.

  an analytic `dE/dε` — 18-12 and 18-13 deliver. It is a reasonable thing to
  want; it is not a port, and the distinction is what keeps the drop-in claim
  honest.
</task>
