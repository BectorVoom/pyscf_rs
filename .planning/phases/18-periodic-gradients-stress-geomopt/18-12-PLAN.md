<task type="auto">
  <name>Task 1: the eight shared symbols, and one `Ls` for all 36 lattice sums (clause 2)</name>
  Port `strain_tensor_dispalcement` (`:59`), `_get_weight_strain_derivatives`
  (`:121`), `_get_coulG_strain_derivatives` (`:112`), `get_ovlp` (`:86`),
  `get_kin` (`:99`), `_get_vpplocG_strain_derivatives` (`:292`),
  `_get_pp_nonloc_strain_derivatives` (`:309`) and `ewald` (`:387`).
  `_finite_diff_cells` and `_eval_ao_strain_derivatives` came from 18-02 Task 5
  and 18-11.

  **`get_ovlp` and `get_kin` are 36 lattice sums between them** — 9 strain
  components × 2 displaced cells × 2 operators — and each re-derives `Ls`
  through `lattice_images` → `get_lattice_ls`, which this port's own doc
  comment calls *"an `O(nimgs · natm)` filter"*. Plan 10-06 already built the
  hook: `intor_cross_with_images(intor, cell1, cell2, kpts, opts, ls,
  neighbor_list)` (`pbc_intor.rs:295`).

  Build `Ls` **once** from the undisplaced cell and pass it to all 36. This is
  also more accurate, not merely faster: at `disp = 1e-5` on 3–5 Bohr lattice
  vectors, `rcut` moves by ~1e-5 relative, so an image on the screening
  boundary can enter one displaced cell's list and not the other's, putting a
  step of order `cell.precision` (1e-8) into a difference upstream itself
  accepts at 1e-8. A shared `Ls` removes that term exactly.

  Test: shared-`Ls` vs per-cell-`Ls` on every reference cell, difference
  recorded, at Gate A's 1e-8. The claim that this is a no-op-or-better is
  measured, not asserted.
</task>

<task type="auto">
  <name>Task 2: the block loop, sized against BOTH AO arrays (clause 1)</name>
  `get_vxc`'s loop (`:200-248`) holds two arrays per block:

  | array | GGA element count |
  |---|---|
  | `ao` from `block_loop(cell, grids, nao, deriv+1)` | `10 · blk · nao` |
  | `ao_strain` from `_eval_ao_strain_derivatives(deriv)` | `36 · blk · nao` |

  `block_loop` chooses `blk` from `max_memory` against **the first array only**
  — it never sees the second. Upstream's blocking therefore under-counts the
  block's true footprint by **4.6× for GGA/MGGA** (`10` vs `10 + 36`) and
  **3.25× for LDA** (`4` vs `4 + 9`). At the k-point scale 18-13 inherits, that
  is a 1.14 GiB block on diamond `gth-dzvp` 2×2×2 (`18-REVIEW §3.1`), on a
  machine where 17-12's host suite is SIGKILLed at exit 137.

  Size the blocks here, against the **sum**, from `PYSCF_MAX_MEMORY`
  (`aftdf.rs:84-85`). Test: pin a low budget and assert the chosen `blk`
  shrinks accordingly, so a budget that silently ignores the larger array fails
  a test rather than the OOM killer.
</task>

<task type="auto">
  <name>Task 3: `get_vxc` — fuse the XC contraction, keep two arrays full-grid (clause 7)</name>
  Port `:148-290`. Upstream allocates `rho1 = np.empty((3,3,nvar,ngrids))`
  (`:191`) over the full grid. Its only full-grid consumers are
  `einsum('xyng,ng->xy', rho1, vxc)` (`:259`) and, for the `with_j`/`with_nuc`
  terms, `rho1[:,:,0]` alone (`:267`, `:276`, `:287`).

  The XC functional is **pointwise in `rho0`**, so `vxc[:,g]` depends only on
  `rho0[:,g]` and the first contraction can be evaluated per block and
  accumulated into the 3×3 output. Keep full-grid: `rho0` (needed by
  `pbctools.fft(rho0[0], mesh)` at `:264`, and no larger than a normal DFT run
  already carries) and `rho1[:,:,0]`. Drop `rho1[:,:,1:nvar]` — a **4× (GGA) /
  5× (MGGA)** cut on that array.

  **Block accumulation changes the summation order** relative to the full
  einsum. The 3×3 accumulator must route through a materialised per-block
  partial array and `pyscf_algebra::oracle_sum` — the D-PBC-17 pattern applied
  to `ztrace_ab`/`trace_dm_v` in commit `0bcff45`, and required of
  `symmetrize_density` by `17-CONTEXT` *"from the first version, not as a
  retrofit."*

  Also fold the post-loop scalings into the block: `rho0[1:4] *= 2`,
  `rho0[4] *= .5`, `rho1[:,:,4] *= .5`, `rho1 *= 2.` (`:250-256`). The last one
  applies to the whole array and is easy to lose when the array stops being
  whole.

  Honest sizing (`18-REVIEW §3.8`): this is a 4–5× cut on a 6.7 MiB
  (`ngrids = 24389`) to 59 MiB (`60³`) array — an order of magnitude below
  clauses 1 and 3. It is done because it is nearly free once the loop is being
  rewritten for Task 2, not because it is where the memory is.
</task>

<task type="auto">
  <name>Task 5: `kernel` and the reported units</name>
  Port `:398-462`. **The result is a pressure.** Upstream's own acceptance is
  `abs(dat[i,j] - (e1-e2)/2e-3/vol) < 1e-6` (`:406`) — `dE/dε` divided by the
  cell volume, Ha/Bohr³. `ROADMAP.md` and `§8.10` both state the gate as
  "1e-5 Ha", which is the wrong dimension and, read as an energy, ~8× tighter
  than upstream's own number (`18-CONTEXT §2.2`).

  Return Ha/Bohr³, say so in the type's doc comment, and name `vol` in the
  gate expression so the dimension cannot drift again.

  **MGGA is supported here** (`:176-178`), unlike the gradient half, which
  refuses it (18-07 Task 1). That asymmetry is upstream's shape; record it in
  the module doc so nobody reconciles the two.
</task>
