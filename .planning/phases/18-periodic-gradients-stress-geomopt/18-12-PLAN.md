  <name>Task 1: the eight shared symbols, and the closed form that replaces 36 lattice sums (D-PBC-31 clause 2)</name>
  Port `strain_tensor_dispalcement` (`:59`), `_get_weight_strain_derivatives`
  (`:121`), `_get_coulG_strain_derivatives` (`:112`), `get_ovlp` (`:86`),
  `get_kin` (`:99`), `_get_vpplocG_strain_derivatives` (`:292`),
  `_get_pp_nonloc_strain_derivatives` (`:309`) and `ewald` (`:387`).
  `_finite_diff_cells` and `_eval_ao_strain_derivatives` came from 18-02 Task 5
  and 18-11.

  Two exact structural facts in that list, made explicit rather than left
  emergent-to-roundoff (D-PBC-31 clause 6):
  * `_get_coulG_strain_derivatives` (`:112-119`) builds
    `coulG_1 = einsum('gx,gy->xyg', Gv, Gv) * coulG_0 * 2/G2` — **symmetric in
    `(x,y)` by construction**. Store and contract the 6 unique components and
    mirror: 1.5× on a 1.7 MiB (`ngrids = 24389`) to 15.5 MiB (`60³`) array.
  * `_get_weight_strain_derivatives` (`:121-125`) returns
    `weight_1 = np.eye(3) * weight_0` — **exactly diagonal**, so `:260`'s
    `einsum('g,g->', rho0[0], exc) * weight_1` is a scalar on the diagonal.
    Add it as one.

  Neither is large. Both matter because the **total** stress is not symmetric
  in general, so an asymmetry that shows up must be attributable to a term that
  is genuinely asymmetric rather than to roundoff in one that is not.

  **`get_ovlp` and `get_kin` are 36 lattice sums between them as upstream
  writes them** — 9 strain components × 2 displaced cells × 2 operators, each
  over a rebuilt cell. D-PBC-30 clause 2 shared one `Ls` across all 36. **This
  plan does better: it does not compute them by finite difference at all**
  (D-PBC-31 clause 2, `18-REVIEW §6.2`).

  Upstream's own test replaces the whole finite difference with a closed form
  and asserts it at **1e-9**, twice, in two algebraically distinct arrangements
  (`test_rks_stress.py:53-71` for ovlp, `:88-107` for kin):

  ```python
  bas_coords = np.repeat(cell.atom_coords(), ao_repeats, axis=0)
  ovlp10 = np.einsum('xij,iy->xyij', cell.pbc_intor('int1e_ipovlp'), bas_coords)
  sc_ovlp01 = intor_cross('int1e_ipovlp', scell, cell)      # scell = supercell over Ls
  ovlp01 = np.einsum('xinj,njy->xyij', sc_ovlp01, bas_coords + Ls[:,None])
  dat = -(ovlp10 + ovlp01)[0, 1]
  assert abs(dat - ref).max() < 1e-9        # ref = the 1e-5 central difference
  ```

  Derived:
  `dS_k/dε_xy = −Σ_L e^{ik·L} [ ∇_x S[i,j;L]·R_{i,y} + ∇^{ket}_x S[i,j;L]·(R_j+L)_y ]`,
  and the weight **splits**: `R_{j,y}` is AO-indexed and applies *after* the
  lattice sum; `L_y` is an image scalar and folds straight into the Bloch-phase
  array — **18-02 Task 7's hook**. So the port needs no supercell and no new
  integral family: the whole 3×3 derivative is one `int1e_ipovlp` lattice sum
  run with four phase rows per k-point instead of one.

  | | upstream, as written | this task |
  |---|---|---|
  | lattice sums, ovlp + kin | 36 | **2** |
  | displaced cell builds | 36 | **0** |
  | `get_lattice_ls` calls | 36 | 1 |
  | truncation error | `O(disp²)` | **none** |
  | cancellation error | `2·ε·|S|/2e-5 ≈ 2e-11` | **none** |
  | screening discontinuity | ≤ `cell.precision` | **none** |

  **Port both of upstream's arrangements** — `-(ovlp10 + ovlp01)` from
  `intor_cross(scell, cell)` and `-(ovlp10 - ovlp01)` from
  `intor_cross(cell, scell)`. They differ by which side carries `∇`, so a sign
  error in the ket-derivative term cancels in one and not the other, and
  upstream asserts both.

  Tests: (1) closed form vs the finite-difference oracle at **1e-9**, upstream's
  own number for exactly this substitution, on every reference cell;
  (2) the two arrangements agree with each other; (3) the FD oracle itself
  builds each `±` cell pair **once** and runs both operators on it — 36 → 18
  cell builds in the gate (D-PBC-31 clause 11).

  D-PBC-30 clause 2 survives only for the finite differences that remain, i.e.
  the ones inside this gate: a shared `Ls` across the two sides of a difference
  still removes a step discontinuity. **Part I's claim that this is a
  "1e-8-order" win is an upper bound, not a realised one** — upstream's own
  analytic-vs-FD assertion passes at 1e-9 on its fixture, so the realised
  discontinuity is below that (`18-REVIEW §6.2`).
</task>

  <name>Task 2: the block loop, sized against BOTH AO arrays (clause 1)</name>
  `get_vxc`'s loop (`:200-248`) holds two arrays per block:

  | array | GGA element count |
  |---|---|
  | `ao` from `block_loop(cell, grids, nao, deriv+1)` | `10 · blk · nao` |
  | `ao_strain` from `_eval_ao_strain_derivatives(deriv)` | `36 · blk · nao` |

  `block_loop` chooses `blk` from `max_memory` against **the first array only**
  — it never sees the second. Upstream's blocking therefore under-counts the
  block's true footprint by **4.6× for GGA/MGGA** (`10` vs `10 + 36`) and
  **3.25× for LDA** (`4` vs `4 + 9`). At the k-point scale 18-13 inherits, that
  is a 1.14 GiB block on diamond `gth-dzvp` 2×2×2 (`18-REVIEW §3.1`), on a
  machine where 17-12's host suite is SIGKILLed at exit 137.

  Size the blocks here, against the **sum**, from `PYSCF_MAX_MEMORY`
  (`aftdf.rs:84-85`). Test: pin a low budget and assert the chosen `blk`
  shrinks accordingly, so a budget that silently ignores the larger array fails
  a test rather than the OOM killer.
</task>

  <name>Task 3: `get_vxc` — fuse the XC contraction, keep two arrays full-grid (clause 7)</name>
  Port `:148-290`. Upstream allocates `rho1 = np.empty((3,3,nvar,ngrids))`
  (`:191`) over the full grid. Its only full-grid consumers are
  `einsum('xyng,ng->xy', rho1, vxc)` (`:259`) and, for the `with_j`/`with_nuc`
  terms, `rho1[:,:,0]` alone (`:267`, `:276`, `:287`).

  The XC functional is **pointwise in `rho0`**, so `vxc[:,g]` depends only on
  `rho0[:,g]` and the first contraction can be evaluated per block and
  accumulated into the 3×3 output. Keep full-grid: `rho0` (needed by
  `pbctools.fft(rho0[0], mesh)` at `:264`, and no larger than a normal DFT run
  already carries) and `rho1[:,:,0]`. Drop `rho1[:,:,1:nvar]` — a **4× (GGA) /
  5× (MGGA)** cut on that array.

  **Block accumulation changes the summation order** relative to the full
  einsum. The 3×3 accumulator must route through a materialised per-block
  partial array and `pyscf_algebra::oracle_sum` — the D-PBC-17 pattern applied
  to `ztrace_ab`/`trace_dm_v` in commit `0bcff45`, and required of
  `symmetrize_density` by `17-CONTEXT` *"from the first version, not as a
  retrofit."*

  Also fold the post-loop scalings into the block: `rho0[1:4] *= 2`,
  `rho0[4] *= .5`, `rho1[:,:,4] *= .5`, `rho1 *= 2.` (`:250-256`). The last one
  applies to the whole array and is easy to lose when the array stops being
  whole.

  Honest sizing (`18-REVIEW §3.8`): this is a 4–5× cut on a 6.7 MiB
  (`ngrids = 24389`) to 59 MiB (`60³`) array — an order of magnitude below
  clauses 1 and 3. It is done because it is nearly free once the loop is being
  rewritten for Task 2, not because it is where the memory is.
</task>

  `abs(dat[i,j] - (e1-e2)/2e-3/vol) < 1e-6` (`:406`) — `dE/dε` divided by the
  cell volume, Ha/Bohr³. `ROADMAP.md` and `§8.10` both state the gate as

  than upstream's own number (`18-CONTEXT §2.2`).

  gate expression so the dimension cannot drift again.

  refuses it (18-07 Task 1). That asymmetry is upstream's shape; record it in
  the module doc so nobody reconciles the two.
</task>
