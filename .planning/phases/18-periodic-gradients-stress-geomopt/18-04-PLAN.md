<objective>
The two-electron half of every k-point gradient, and the only density-fitting
route in PySCF 2.12.1 that has one.

`grep -rn "def get_jk_e1\|def get_j_e1\|def get_k_e1" pyscf/pbc/df/*.py` returns
three lines, all in `fft.py` (`:324`, `:330`, `:335`), and the class graph shows
`GDF`, `RSGDF`, `MDF` and `AFTDF` are **not** FFTDF subclasses
(`18-CONTEXT §1.2`). So `krhf.GradientsBase.get_jk`'s
`self.base.with_df.get_jk_e1(...)` (`krhf.py:265`) raises `AttributeError` on
every other route, and there is no periodic analytic gradient for GDF/MDF/RSDF
anywhere upstream. This port defaults `KRHF` to FFTDF already
(`crates/pyscf-pbc-scf/src/krhf.rs:46`) — but a user who calls
`.density_fit()` must get a loud, named refusal, not a plausible wrong number
from a substituted route.

This plan also lands **three of the seven D-PBC-30 clauses** (3, 4a, 4b),
because they are all properties of this one file.
</objective>

<tasks>

<task type="auto">
  <name>Task 1: `get_j_e1_kpts`</name>
  Port `fft_jk.py:113-...`. It differentiates the AOs on the real-space grid
  via `eval_ao_kpts(deriv=1)` and reuses the same FFT/`coulG` pipeline as the
  energy — `int2e_ip1` is never called. The port's `get_j_kpts`
  (`fft_jk.rs:55`) already owns that pipeline; the derivative version differs
  only in which AO component sits on the bra and in the leading `(3, …)`
  component axis.

  Build it beside `get_j_kpts` in a sibling module, sharing the `coulG` cache
  the energy path already has (W-01), not re-deriving it.
</task>

<task type="auto">
  <name>Task 2: the budgeted k-point AO table (D-PBC-30 clause 3)</name>
  `fft_jk.py:346-350` builds `ao1_kpts` for **all** k-points at `deriv = 1`
  before the loop — `nkpts · 4 · ngrids · nao` complex, which
  `18-REVIEW §3.1` sizes at **1.02 GiB** for diamond `gth-dzvp` at 3×3×3 — and
  `blksize` (`:363`) guards only the inner `rho1`, not this. The grid cannot be
  blocked (the FFT at `:392` needs it whole), so the only lever is how many
  k-points are resident.

  Ship `ao_cache.rs`: a table sized from `PYSCF_MAX_MEMORY` (the
  `aftdf.rs:84-85` precedent) with two branches —
  * **resident**: all k-points held, when the table fits;
  * **streaming**: only the two k-points in flight, recomputed per pair. Peak
    drops to `2 · 4 · ngrids · nao` (an `nkpts/2` reduction) and is paid for in
    `nkpts`× AO re-evaluation.

  Re-derive `blksize` for the inner `rho1`. **Do not transcribe upstream's**:
  `:362` already subtracts `mem_now` from `max_memory` and `:363` subtracts it
  again, so upstream's block is smaller than its own budget intends
  (`18-CONTEXT §3.7`).

  This module is shared with 18-05 Task 3 (clause 6) — one cache, one budget,
  two consumers. Two independent budgets that each believe they own the machine
  is how a 1 GiB array becomes 2 GiB.
</task>

<task type="auto">
  <name>Task 3: `get_k_e1_kpts`, with the MO factorisation (clause 4a)</name>
  Port `fft_jk.py:310-...`. When the density carries the `mo_coeff`/`mo_occ`
  tag 18-02 Task 3 built, `:357-359` collapses the ket index from `nao` to the
  occupied count. `18-REVIEW §3.1` sizes the inner `rho1` at **755 MiB**
  untagged and **116 MiB** tagged on diamond `gth-dzvp` — a 6.5× cut, and 2×
  even on `gth-szv`.

  Both routes ship. Gate them against each other: the tagged and untagged
  results agree at 18-01's measured tolerance, and the tagged one's peak
  allocation is strictly smaller. An optimisation with no test that it *was*
  taken is an optimisation that silently stops being taken.
</task>

<task type="auto">
  <name>Task 4: the named refusal for every non-FFTDF route</name>
  `Fftdf` gains `get_jk_e1` / `get_j_e1` / `get_k_e1`. Every other
  `PeriodicDf` implementor gains the same three methods returning an error that
  **names the route and says why**: PySCF 2.12.1 has no periodic analytic
  gradient for GDF/MDF/RSDF/AFTDF, and the fix is to run the gradient on FFTDF,
  not to substitute a route.

  Test (`grad_route_refusal.rs`): construct a `KRHF` on each of GDF, MDF, RSDF
  and AFTDF, ask for the gradient JK, and assert the error names the route.
  **Assert it is an error, not a number** — a fallback here would produce a
  gradient that is plausible, wrong, and consistent run to run.
</task>

<task type="auto">
  <name>Task 5: refuse `kk_symmetry` on the gradient route (clause 4b)</name>
  `fft_jk.rs:265-330` documents the energy-path identity
  `rho1^{21}[(i,j),g] = conj(rho1^{12}[(j,i),g])`, which halves the transforms
  and which its own doc block warns *"CHANGES THE RESULT … must be
  re-baselined"*. It holds because bra and ket carry the same AO table.

  In `get_k_e1_kpts` the bra is `ao1T[1:,p0:p1]` — the **derivative** AO — and
  the ket is `ao2T`. The `(j,i)` swap moves the derivative onto the ket and the
  identity does not close.

  The gradient entry point therefore takes no `kk_symmetry` flag, and if the
  builder carries one it **refuses** rather than ignoring it. Test the refusal.
  A comment asking implementers not to enable it is not a mechanism, and a
  wrongly enabled flag here moves the last bits of an otherwise-correct
  gradient — the hardest class of error to attribute.
</task>

<task type="auto">

</task>
