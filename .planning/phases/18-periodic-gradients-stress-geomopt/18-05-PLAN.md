<task type="auto">
  <name>Task 2: `hcore_generator` — port the closure, not the loop nest</name>
  Port `krhf.py:117-147`. The per-atom derivative is
  `vloc_g = 1j · Gv · SI[atm] · vlocG[atm]`, inverse-FFT'd per Cartesian
  component and contracted against the AO table, minus the `h1` rows and
  columns belonging to that atom (`:144-145`).

  **Watch the index order at `:144-145`:**
  ```python
  hcore[:,kn,p0:p1]   -= h1[kn,:,p0:p1]
  hcore[:,kn,:,p0:p1] -= h1[kn,:,p0:p1].transpose(0,2,1).conj()
  ```
  the second term is the **conjugate transpose** of the same block, not a
  second slice. `crates/pyscf-pbc-scf/src/types.rs:119` records that this
  port's `mo_coeff` is column-major; 14-05's `decompose_j2c` misread of exactly
  this kind was worth +6 306 866.73 Ha and was invisible to every gate then
  existing. Gate it with a deliberately non-Hermitian test matrix so a missing
  `.conj()` fails rather than cancels.
</task>

<task type="auto">
  <name>Task 3: don't hoist the AO table — delete the loop that needs it (D-PBC-31 clause 7)</name>
  D-PBC-30 clause 6 ruled that the AO table be hoisted out of
  `hcore_generator`'s atom loop. That is the right direction and it does not go
  far enough: **there is no reason to build the matrix at all.**

  Upstream's closure (`krhf.py:132-147`) allocates `(3, nkpts, nao, nao)` per
  atom and fills it with
  ```python
  vloc = np.einsum('gi,gj,g->ij', ao.conj(), ao, vloc_R, optimize=True)
  ```
  at cost `natm · 3 · nkpts · ngrids · nao²` — and `grad_elec:63` reduces the
  whole thing to three numbers against `dm0`. But
  ```
  Σ_ij vloc[k,i,j]·dm0[k,j,i] = Σ_g vloc_R[g]·ρ_k[g] = Σ_G conj(vloc_g[G])·ρ_k[G]
  ```
  and **ρ depends on neither `atm_id` nor the Cartesian component.** The entire
  per-atom loop is one `(natm,3) ← (natm·3, ngrids) × (ngrids)` contraction
  against a density the SCF already knows how to build.

  | | ported literally | clause 6 (hoist) | this ruling |
  |---|---|---|---|
  | AO-table evaluations | `natm · nkpts` | `nkpts` | `nkpts` |
  | `ngrids · nao²` work | `natm · 3 · nkpts` | `natm · 3 · nkpts` | **`nkpts`** |
  | inverse FFTs | `natm · 3` | `natm · 3` | **0** (contract in G-space) |
  | resident per-atom array | `3·nkpts·nao²` complex | same | **none** |

  6× on the `ngrids·nao²` term at `natm = 2`, `3·natm`× on anything worth
  optimising a geometry for. **This subsumes D-PBC-30 clause 6** — there is no
  per-atom AO cost left to hoist. 18-04's `ao_cache` is still the one budget
  for `get_hcore`'s `h1` build; it no longer serves a per-atom hoist.

  Two constraints that make this a ruling and not a rewrite:

  * **`hcore_generator` stays a public seam returning the matrix.**
    `grad_elec:68` passes `locals()` to `extra_force` and 18-08's DFT+U term
    reads it; the component-level gate needs the matrix too. The fused
    contraction is what `grad_elec` **uses**; the matrix is what the API
    **exposes**. A test asserts the two agree.
  * **G-space and real-space are different summations.** Parseval is exact in
    exact arithmetic and ~1e-13 relative in this one. Gate against **18-01
    Task 5b's measured residual**, and do not claim bit-identity — a fused
    route that quietly moved the last bits of every gradient in the phase is
    the hardest class of error to attribute.

  The contraction itself is **18-09 Task 2's shared primitive** (D-PBC-31
  clause 10), not a fourth implementation of the same reduction. **If 18-09
  has landed, call it; if this plan lands first, write it there and have
  18-09 call it** (the same forward-reference 18-03 Task 5 resolves for the
  Ewald gradient). One implementation either way, and one determinism test —
  do not write a local copy "for now."

  Tests: (1) AO evaluations per `grad_elec` is `nkpts`, not `natm · nkpts`;
  (2) the `ngrids·nao²` work counter does not scale with `natm`;
  (3) the fused scalar equals `hcore_deriv(ia)` contracted with `dm0`, at
  18-01 Task 5b's number.
</task>

<task type="auto">
  <name>Task 4: `grad_elec` — the assembly, in upstream's exact order</name>
  Port `krhf.py:34-74`. Three contractions per atom, then two out-of-loop
  terms, and the scopes are not what they look like:

  ```python
  de[x] += einsum('xkij,kji->x', h1ao, dm0).real
  de[x] += einsum('xkij,kji->x', vhf[:,:,p0:p1], dm0[:,:,p0:p1]).real * 2
  de[x] -= einsum('kxij,kji->x', s1[:,:,p0:p1], dme0[:,:,p0:p1]).real * 2
  de[x] /= nkpts                       # :67 — INSIDE the atom loop
  de[x] += mf_grad.extra_force(ia, locals())   # :68 — AFTER the division
  ...
  de += pp_int.vppnl_nuc_grad(cell, dm0, kpts) / nkpts   # :69 — whole array
  ```

  Three points that a literal port gets right and a tidy one gets wrong:
  * the DM is indexed **`kji`**, not `kij`, on all three terms;
  * `s1`'s component axis is **`kxij`** — k first, then component — while
    `h1ao` and `vhf` are `xkij`. That is not a typo in upstream; `get_ovlp`
    returns `pbc_intor`'s native `(nkpts, 3, nao, nao)` while `hcore_generator`
    builds `(3, nkpts, nao, nao)`;
  * `extra_force` is added after the `/= nkpts`, so it is **not** divided.

  **Take the real part inside each contraction, not after it** (D-PBC-31
  clause 4). All three terms are `einsum(...).real`, and
  `Re(Σ a·b) = Σ (Re a·Re b − Im a·Im b)` **exactly** for a fixed summation
  order — complex addition is componentwise, so nothing rounds differently.
  Computing only the real part halves the multiplies (2 per product instead of
  4) and removes the complex accumulator entirely.

  All three accumulators route through `oracle_sum` over materialised partial
  buffers (D-PBC-17) — **real** buffers, per the clause above. Gate the index
  order with a non-symmetric DM, and gate the clause-4 rewrite by asserting it
  is bit-identical to the complex-then-`.real` route on that same DM.
</task>
