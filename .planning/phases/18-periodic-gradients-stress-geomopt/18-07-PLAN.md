<objective>
`pyscf/pbc/grad/krks.py` (141 l) and `kuks.py` (135 l) — the k-point Kohn–Sham
gradients. Structurally they are 18-05/18-06's assembly with `get_veff`
replaced by an XC-grid term plus the Coulomb/hybrid-exchange terms.

The reason this is not a mechanical port is **what upstream refuses**. Three
capabilities the molecular port already ships are `raise NotImplementedError`
here, and inheriting them would make this port *more capable than upstream* on
the drop-in surface — which is a fidelity defect, not a feature.
</objective>

  <name>Task 1: the three refusals, written before the bodies</name>
  * **`grid_response`.** `krks.py:48-49` and `kuks.py:49-50` are
    `if ks_grad.grid_response: raise NotImplementedError`, and `kuks.py:129`
    hard-sets `self.grid_response = False` in `__init__`. The molecular
    `crates/pyscf-grad/src/rks.rs:106-108` documents `grid_response` as
    **"Fully supported"** with an `extra_force` Becke-weight-derivative term.
    The periodic subclass must **override that to a refusal**. This is the one
    place in the phase where inheriting working code produces the wrong
    behaviour, so it is Task 1 and not a footnote.
  * **meta-GGA.** `krks.py:112` / `kuks.py:118` —
    `raise NotImplementedError("metaGGA")`.
  * **NLC / VV10.** `krks.py:110` / `kuks.py:116` —
    `raise NotImplementedError("NLC")`.

  Note the asymmetry with the stress half, and record it in the module doc so
  nobody "fixes" it later: **the stress tensor DOES support meta-GGA**
  (`rks_stress.py:176-178`, and `test_rks_stress.py:426`
  `test_mgga_vs_finite_difference_high_cost`). Gradient = LDA/GGA/HF/hybrid;
  stress = LDA/GGA/MGGA. That is upstream's shape, not an oversight to
  reconcile.
</task>

<task type="auto">
  <name>Task 2: `get_vxc` — the LDA and GGA grid terms</name>
  Port `krks.py:68-117` and `kuks.py:70-120`. Both are a `block_loop` over the
  grid with `ao_deriv = 1` (LDA) or `2` (GGA), building `rho` through
  `_gen_rho_evaluator`, evaluating `eval_xc_eff(deriv=1)`, and accumulating
  into `vmat` per k-point through the **molecular** helpers
  `rks_grad._d1_dot_` (`krks.py:87`) and `rks_grad._gga_grad_sum_` (`:103`).

  **Neither helper exists in this port.** `grep -rn "d1_dot\|gga_grad_sum"
  crates/pyscf-grad/src/` returns nothing; `crates/pyscf-grad/src/rks.rs` does
  the equivalent accumulation **inline** inside a **private** `fn get_vxc`
  (`:328`), so it is not callable from `pyscf-pbc-grad` even if it were the
  right shape.

  **Ruling:** extract the two accumulation primitives out of
  `pyscf-grad::rks::get_vxc` into `pub fn`s in `pyscf-grad`, and have the
  molecular and the periodic `get_vxc` both call them. This follows GRAD-10's
  standing rule for CPHF — *"one implementation only, enforced by the existing
  source-scan gate"* — for the same reason: two AO-derivative accumulators that
  are supposed to agree, and drift, is a bug nobody finds until a GGA gradient
  is quietly wrong in the third decimal.

  The extraction must leave the molecular result **bit-identical**: this task's
  first test is `cargo test -p pyscf-grad` green with an empty behavioural diff,
  the same acceptance 16-02 used when it touched `WorkspacePool`.

  The GGA branch's `wv[0] *= .5` (`:101`) before the sum
  is the factor that makes `_gga_grad_sum_`'s double-counting correct — it is
  easy to drop and it fails only on GGA, so gate LDA and GGA separately.

  The return is **negated**: `return -vmat[:,0]` when `nset == 1`, else
  `-vmat` (`:114-117`). The sign lives here.

  `max_memory` for `block_loop` comes from `PYSCF_MAX_MEMORY`, not from
  transcribing `krks.py:46-47`'s `lib.current_memory()` arithmetic
  (`18-CONTEXT §3.7`).
</task>

<task type="auto">
  <name>Task 3: `get_veff` — Coulomb, hybrid and the range-separated branch</name>
  Port `krks.py:31-64`, `kuks.py:32-67`:

  ```python
  if not ni.libxc.is_hybrid_xc(mf.xc):
      vxc += ks_grad.get_j(dm, kpts)
  else:
      omega, alpha, hyb = ni.rsh_and_hybrid_coeff(mf.xc, spin=cell.spin)
      vj, vk = ks_grad.get_jk(dm, kpts); vk *= hyb
      if omega != 0:
          with cell.with_range_coulomb(omega):
              vk += ks_grad.get_k(dm, kpts) * (alpha - hyb)
      vxc += vj - vk * .5
  ```

  The RSH branch re-enters `get_k` under a modified Coulomb kernel with
  coefficient `(alpha - hyb)`. 18-04's `get_k_e1_kpts` takes `omega` the same
  way `fft_jk.rs`'s energy path does, so this route is available on FFTDF —
  unlike the GDF `omega` carry-over that `STATE.md` records as still blocked at
  `gdf/jk.rs:674`. Say which route is which in the doc comment; the two
  blockers are unrelated and will otherwise be conflated.

  `kuks.get_veff` differs only in the spin threading of `vj`/`vk`, exactly as
  18-06 Task 2.
</task>
