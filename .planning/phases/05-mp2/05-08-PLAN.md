<objective>

**Gap-closure for Phase 5: close the cintx#11 numeric gate now that cintx ships
the arity-3/4 two-electron integrals.**

Phase 5 shipped the full MP2 surface (in-core RMP2/UMP2, conventional + native
DF-MP2, RDMs, frozen-core, PyO3 bridge, CCSD import helpers) as **structurally
complete but numerically gated**: every MP2 numeric path `?`-propagates the
`int2e` / `int3c2e_sph` integrals that were `NotYetImplemented{phase:2}` (in-core)
or returned an all-zeros buffer (DF). The phase was designed (D-05) so that
"numeric energy flips on with no code change once the integral lands."

cintx has now landed those integrals — exactly mirroring how the cintx Phase-19/20
workstream shipped `int1e_ecp_*` and unblocked the 02-10 GTO-05 eval-half closure:

- `int2e_sph` / `int2e_cart` — arity-4, `api_manifest.rs:166/183`, `SHELL_TUPLE_CAPACITY=4`
- `int3c2e_sph` — arity-3, `api_manifest.rs:404`
- Both libcint-byte-identical at the cintx source (`safe_api_arity4_parity.rs`,
  `safe_api_arity3_parity.rs`, `two_electron_parity.rs`, `center_3c2e_parity.rs`),
  and cintx-rs now *asserts* against all-zero output (`api.rs:750` "regression to
  zero-fill stub?").

This plan implements the **pyscf-gto dispatch** that consumes those operators
(the one missing layer), verifies the MP2 numerics light up in-tree, and follows
the 02-10 precedent for the parts that need upstream PySCF (CI-gated/human-verify).

This is foundationally a pyscf-gto (Phase 2 `intor`) closure; it also unblocks
DF-HF (Phase 3) and bit-exact RKS/UKS (Phase 4), but those are out of scope here —
this plan asserts only the MP2-facing surface (MP2-01/02/04/05 numeric halves).

**No new crate dependency. cintx stays a path-dep at the already-merged tree
(Cargo.lock unchanged — same topology as 02-10). libxc is NEVER compiled.**

**cintx safe API (already used by evaluate_arity2 — extend, don't reinvent):**
```rust
let request = SessionRequest::new(operator, representation, basis, shells, ExecutionOptions::default());
let outcome = request.query_workspace()?.evaluate()?;
let block = &outcome.tensor.owned_values;       // F-order, libcint layout
let extents = &outcome.tensor.extents;
```
- `basis.shell_tuple_for_indices([i,j,k,l])` → `ShellTuple` (capacity 4, so arity-4 OK).
- Arity ≥ 3 blocks are F-order, byte-identical to vendor libcint (cintx api.rs:531).

**int2e (arity-4):** iterate (i,j,k,l) over the SAME `mol.cintx_basis()` shells;
per-quad block `[ni,nj,nk,nl]` F-order; stitch into global `[nao,nao,nao,nao]`
F-order: `out[p + q*nao + r*nao^2 + s*nao^3]` where p=oi+ii, q=oj+jj, r=ok+kk, s=ol+ll.

**int3c2e (arity-3, orbital×aux):** PySCF fakemol pattern — combine `mol` (orbital)
and `auxmol` (aux) into ONE cintx BasisSet, then iterate (i,j ∈ orbital shells,
k ∈ aux shells, k offset by nbas_orbital). `projection.rs::build_cintx_basis_set`
(and the `_with_ecp` variant) already builds a BasisSet from ParsedAtom+ParsedBasis
via `BasisSet::try_new(atoms_arc, shells_arc)`; add a combined builder that
concatenates mol's atoms+shells with auxmol's (offsetting aux shell→atom indices).
Resolve the exact combine idiom at execution by reading projection.rs's private
`build_*` helper + cintx_core BasisSet/Shell `atom_index`.

**Consumers (UNCHANGED — they already `?`-propagate the gate, D-05):**
- `crates/pyscf-mp2/src/mp2.rs::default_ao2mo` → `pyscf_gto::intor(&mol, "int2e")`
- `crates/pyscf-df/src/cholesky_eri.rs::cholesky_eri` → `intor_with_auxmol(mol,"int3c2e_sph",auxmol)`

**Verification reality (02-10 precedent):** the sandbox has no numpy/upstream-PySCF,
