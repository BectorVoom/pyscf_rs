<objective>
`KptsHelper` — `pyscf/pbc/lib/kpts_helper.py:544-632`. The small, entirely
self-contained piece of Phase 15, and the one Phase 16 will lean on hardest.

`KMP2.__init__` builds one (`kmp2.py:715`, `:723`) and `kmp2.kernel` reads
**only `khelper.kconserv`** from it (`kmp2.py:93`). The `symm_map` /
`transform_symm` half is what KCCSD uses to compute one ERI block per symmetry
orbit instead of `nkpts³` of them. Both halves ship here, because they are
forty lines together and splitting them across two phases would leave the
harder half untested.

**Explicitly NOT in this plan:** `get_kconserv`/`get_kconserv3` (shipped by
09-07, `crates/pyscf-pbc-lib/src/kpts_helper.rs`) and `ktensor.py` (a k-point
SYMMETRY container whose only consumers are the `*_ksymm` modules — Phase 17;
see `15-CONTEXT.md §1.1`).
</objective>

<task type="auto">
  <name>Task 2: crates/pyscf-pbc-lib/src/khelper.rs — the type</name>
  A new module (not an addition to `kpts_helper.rs`, which is already large and
  is the *free-function* module).

  ```rust
  pub struct KptsHelper {
      pub kconserv: Kconserv,
      pub nkpts: usize,
      /// `symm_map[(kp,kq,kr)] = [(kp,kq,kr), ...]` — insertion-ordered.
      pub symm_map: Option<IndexMap<[usize; 3], Vec<[usize; 3]>>>,
      /// `_operation[kp,kq,kr] ∈ 0..=3`, flat `nkpts³`.
      operation: Option<Vec<u8>>,
  }
  ```

  * `KptsHelper::new(a: &[[f64;3];3], kpts: &[[f64;3]]) -> Self` — PORT
    `:546-571`, with `init_symm_map = true` as upstream's default. Take
    `cell.a` rather than `&Cell`, matching `get_kconserv`'s existing signature
    (`kpts_helper.rs`); `pyscf-pbc-lib` does not depend on `pyscf-pbc-gto` and
    **must not start**.
  * `KptsHelper::without_symm_map(...)` — the `init_symm_map = False` path, which
    is what KMP2 actually needs. `build_symm_map` is `O(nkpts³)` and KMP2 reads
    only `kconserv`; make the cheap construction reachable by name.
  * `build_symm_map(&mut self, kptlist: Option<&[[usize; 3]]>)` — PORT
    `:573-610` **verbatim, including the order of the four branches**. The
    insertion order of `symm_map` is observable (upstream uses an
    `OrderedDict`) and Phase 16 will iterate it; use an order-preserving map,
    or a `Vec<([usize;3], Vec<[usize;3]>)>` plus a lookup index. Do not use
    `HashMap`.

    **Speed, and why this loop stays single-threaded (15-CONTEXT §7
    corollary):** the function is `O(nkpts³)` and, at the `nkpts = 4096` scale
    Phase 17's Si fixture reaches, that is billions of triples — a real cost
    for whichever Phase-16 caller runs it there. It is tempting to
    `rayon::par_iter` the outer loop, but the "claim on first visit" logic is
    what makes each triple land in exactly one orbit *and* determines which
    member becomes the map key in insertion order — parallelising it changes
    either without a synchronised claim table, and Phase 16 depends on the
    order. **Leave it sequential** and say why in the doc comment, rather than
    silently eating the risk for a speedup nothing here needs yet (KMP2 never
    calls this function — `without_symm_map` below is its path). If a later
    phase needs this faster, the fix is a synchronised claim (e.g. one pass to
    partition orbits in parallel, a second single-threaded pass to fix
    insertion order) — not a bare parallel loop.
  * `transform_symm(&self, eri: &CTensor, nmo: [usize; 4], kp, kq, kr) -> CTensor`
    — PORT `:612-632`. The four operations, in upstream's numbering:

    | op | upstream | meaning |
    |---|---|---|
    | 0 | `eri_kpt` | identity |
    | 1 | `.transpose(2,3,0,1)` | swap the bra and ket PAIRS |
    | 2 | `conj(.transpose(1,0,3,2))` | swap within each pair, conjugate |
    | 3 | `conj(.transpose(3,2,1,0))` | full reversal, conjugate |

    Upstream's `eri_kpt` is `(nmo,nmo,nmo,nmo)`; this port carries four
    possibly-different `nmo` (`Eri7d::nmo` is `[usize; 4]`), so the transposes
    permute the SHAPE too. Get that right or op 1 silently reads out of bounds
    only when the four `nmo` differ — which is exactly the padded case.
  * `operation(&self, kp, kq, kr) -> u8` — accessor; keep the field private so
    nobody indexes the flat vector by hand.

  Every function carries a `PORT:` comment naming the upstream line range
  (RULE 2).

<task type="test">
  <name>Task 4: crates/pyscf-pbc-lib/tests/khelper.rs</name>
  Tier-1 first — this module is pure combinatorics over an existing table, so
  almost everything is checkable with no oracle at all.

  1. **The map is a partition, no oracle.** Over `nkpts ∈ {1, 2, 4, 8}` (from
     `make_kpts` on `diamond` at `[1,1,1] / [1,1,2] / [2,2,1] / [2,2,2]`):
     every one of the `nkpts³` triples appears in **exactly one** `symm_map`
     value, and `completed` reaching all-true is equivalent to that. A missed
     or duplicated triple is the whole failure mode of `build_symm_map`.
  2. **Each orbit's members really are related, no oracle.** For every key
     `(kp,kq,kr)` with `ks = kconserv[kp,kq,kr]`, assert the four listed
     members are exactly the subset of `{(kp,kq,kr), (kr,ks,kp), (kq,kp,ks),
     (ks,kr,kq)}` that had not already been claimed, and that each is
     momentum-conserving under `kconserv`. This is upstream's own invariant
     stated as a test rather than as a comment.
  3. **`transform_symm` round-trips, no oracle.** Build a random complex
     `(n1,n2,n3,n4)` block with four DISTINCT `nmo` values. Applying op `o`
     and then the op that inverts it returns the original **bit-for-bit**
     (`assert_eq!` on the `Vec<f64>` planes). Ops 1 and 3 are self-inverse;
     op 2 is self-inverse. Distinct `nmo` is the point — equal dimensions hide
     a transposed-shape bug.
  4. **`transform_symm` against the physical identity, no oracle.** Take a real
     `Eri7d` block from `pyscf_pbc_df::df_ao2mo::ao2mo_7d` on `he_fcc` 2×2×2 at
     one symmetry-unique `(kp,kq,kr)`, apply `transform_symm` to reach a
     related triple, and compare against `ao2mo_7d`'s OWN entry at that triple.
     **This is the test that matters** — it checks the symmetry relations
     against real integrals rather than against index arithmetic. Tolerance
     1e-13 (both sides come from the same contraction; a looser bound would
     hide an operation mix-up, which produces a similar-magnitude wrong number).
  5. **`without_symm_map` costs nothing.** `symm_map` and `operation` are
     `None`, `kconserv` is identical to the eager form's, and calling
     `transform_symm` returns a clear error rather than panicking.
  6. **Oracle (`PYSCF_ORACLE_VENV`), `#[ignore]`d.** `symm_map` keys and values
     match `kpts_helper.KptsHelper(cell, kpts).symm_map` **exactly, in order**,
     and `_operation` matches element-wise, on diamond `[2,2,2]` and `[1,1,2]`.
     Assert `pyscf.__version__ == "2.12.1"`. Follow the skip-unless-venv
     pattern of `crates/pyscf-pbc-gto/tests/oracle_phase9.rs` so
     `cargo test --workspace` never touches Python.
  7. **The `O(nkpts³)` growth floor (D-PBC-27).** Time `build_symm_map` at
     `nkpts ∈ {8, 27, 64, 125}` (the `diamond`/`si` cubic k-meshes already in
     use) and record wall time and the ratio between consecutive points against
     the `n³` prediction. This is a measurement of the Rust port itself, not of
     upstream — Python has no equivalent benchmark to reproduce — and it is
     what tells Phase 16 whether the sequential-by-design construction above
     is a problem at the k-meshes it actually needs.
</task>
