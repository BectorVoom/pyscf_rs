<objective>
`KMP2` — the phase's reason for existing.

Port target: `pyscf/pbc/mp/kmp2.py` — `kernel` (:45-153),
`_gamma1_intermediates` (:665-690), `make_rdm1` (:567-599),
`make_rdm2` (:602-662), and the `KMP2` class (:692-786).

The formula, with `kb = kconserv[ki,ka,kj]`:

```
e_corr = (1/nkpts) Σ_{ki,kj,ka} Σ_{ijab}
         (ia|jb) · [2·(ia|jb)* − (ib|ja)*] / (ε_i^{ki} + ε_j^{kj} − ε_a^{ka} − ε_b^{kb})
```

Upstream does not write it that way, and **the way it does write it is the
specification**: `oovv_ij[ka]` is built for all `ka` in one pass and then
consumed in a *second* `ka` loop (`kmp2.py:89-96` then `:105-115`), because the
exchange term at `ka` needs the block at `kb`, which the first loop has already
stored. A single fused loop is a different program and gets `exi` wrong for
every `ka` where `kb > ka`.
</objective>

  <name>Task 3: crates/pyscf-pbc-mp/src/kmp2_kernel.rs — the energy</name>
  PORT `kernel` (:45-153), **structure included**.

  * **Memory pre-flight first** (`:70-85`), before any allocation. The two
    formulas verbatim: `nkpts²·naux·nocc·nvir·16/1e6` (DF route only) and
    `nkpts³·(nocc·nvir)²·16/1e6` (when `with_t2`). Reuse
    `pyscf-ccsd`'s `PYSCF_MAX_MEMORY` refusal rather than growing a second one
    (`PBC-MASTER-PLAN §8.8` "Reuse note"); this is its first periodic caller.
    15-01 Task 5 recorded the sizes at the reference systems — check whether the
    arena is actually needed there or only above them, and say which in the
    summary.
  * `Lov` once, up front, when `with_df_ints` (`:104-106` → `lov.rs` from 15-04).
  * The `(ki, kj)` loop containing **two** `ka` loops, in upstream's order.
    First loop fills `oovv_ij[ka]` for all `ka`:
    - DF route: `(1/nkpts)·Σ_L Lov[ki,ka][L,i,a]·Lov[kj,kb][L,j,b]`, then the
      `transpose(0,2,1,3)` that turns `iajb` into `ijab` (`:96`).
    - non-DF route: `with_df.ao2mo([orbo_i, orbv_a, orbo_j, orbv_b],
      [ki,ka,kj,kb], compact=false)`, reshaped `(nocc,nvir,nocc,nvir)`, the same
      transpose, divided by `nkpts` (`:98-104`). Uses 15-04's trait method and
      15-03's `mo_slice`.
  * Second `ka` loop, per `(ki,kj,ka)`:
    - `eia` and `ejb` **filled with `LARGE_DENOM = 1e14`**
      (`pyscf/lib/parameters.py:55`) and then overwritten **only** at
      `(nonzero_opadding[ki] × nonzero_vpadding[ka])` (`:126-136`). 15-CONTEXT
      §3.3: padded orbitals must contribute `~1e-28`, not be skipped. A
      "skip padded entries" implementation is arithmetically different from
      upstream and there is no tolerance at which the difference is zero.
    - `eijab[i,j,a,b] = eia[i,a] + ejb[j,b]` (`direct_sum`, `:137`).
    - `t2_ijab = conj(oovv_ij[ka] / eijab)` (`:110`).
    - `edi = 2·Re Σ_ijab t2[i,j,a,b]·oovv_ij[ka][i,j,a,b]` (`:113`).
    - `exi = −Re Σ_ijab t2[i,j,a,b]·oovv_ij[kb][i,j,b,a]` (`:114` — `'ijab,ijba'`,
      **and it indexes `kb`, not `ka`**).
    - `ss += edi·0.5 + exi`; `os += edi·0.5` (`:115-116`).
  * Both totals divided by `nkpts` at the end (`:118-119`) — the second
    division.
  * **Determinism (§9.3, D-PBC-17).** `edi` and `exi` are contractions over
    `nocc²·nvir²`, and `ss`/`os` accumulate over `nkpts³` of them. Route the
    inner contractions through `pyscf_algebra::oracle_dot` and the outer
    accumulation through `oracle_sum` — the same FOUND-06 pairwise tree that
    `fft_jk` had to adopt in W-05 (`.planning/pbc/SUMMARY.md`). Do this in the
    first version, not as a follow-up: retro-fitting it breaks bit-parity and
    then there is nothing to compare against.
  * **Speed (D-PBC-27, 15-CONTEXT §7).** The `(ki, kj)` outer loop's two
    passes are independent across `(ki, kj)` — each pair only reads
    `Lov`/`ao2mo` blocks and mo slices addressed by its own indices — so
    parallelise that outer loop with rayon. It is a **different** obligation
    from the determinism bullet above: parallelising the loop makes the *work*
    concurrent, while `oracle_sum`/`oracle_dot` make the *reduction into
    `emp2_ss`/`emp2_os`* order-independent. Ship both together; a
    rayon-parallel loop feeding a naively-summed accumulator is exactly the
    half-measure that produces a thread-count-dependent `e_corr`.
  * **Do not exploit `KptsHelper.symm_map`'s 8-fold ERI symmetry here.**
    15-CONTEXT §7's corollary records why: the dominant per-triple cost is this
    same `nocc²·nvir²` contraction, which every member of a symmetry orbit
    still pays once its block is recovered by `transform_symm`, so the 8-fold
    reduction would only shrink the cheaper `oovv`-assembly step, at the price
    of `build_symm_map`'s own `O(nkpts³)` construction (15-02). Upstream's own
    `kmp2.kernel` does not use it either (`kmp2.py:93` reads only
    `khelper.kconserv`). `Kmp2` therefore keeps building `khelper` with
    `KptsHelper::without_symm_map` (Task 2) — do not "upgrade" this to the
    eager form in the name of speed.
  * `t2[ki,kj,ka]` stored when `with_t2` — note the index order is
    `[ki][kj][ka]` while the loop that produced it names `ka` innermost, and
    `_gamma1_intermediates` reads `t2[ki][kj][ka]` and `t2[ki][kj][kb]`
    (`:685-689`). Getting this wrong is invisible in `e_corr` and wrong in
    every density matrix.
